## 一、修订目标

**核心方向：保留可信性，减少交接；收缩模型需要操作的表面，而不是重写全部底层。**

当前主要问题不是能力数量本身，而是三种边界混在了一起：

1. **科学决策边界：**需要判断是否换假设、补证据或改变实验。
2. **责任与权限边界：**需要独立审查、人工批准或受控外部执行。
3. **机械处理边界：**字段展开、对象投影、身份配对、分页和派发。

前两种边界通常值得保留；第三种不应反复交给 Root。

### 1.1 战略目标

将系统从：

> Root 逐项操作科研协议，串联大量小节点。

改为：

> Root 选择一个有价值的研究任务；模块内部连续完成工作；在真正需要决策、独立性或新权限时交接。

主要衡量对象是任务交付和决策成本，不是删除的文件数、Operation 数或代码行数。

### 1.2 非目标

本策略不要求：

- 将全部能力强行压成四个万能 Operation；
- 删除全部 handoff、Schema 或独立审查；
- 合并 Run、Approval、Execution；
- 为四个模块增加新的状态机；
- 新建总协调 Agent、handoff Agent 或必经摘要 Agent；
- 全面支持新领域、新平台、新求解器或强隔离后端；
- 保证 Fig.4 得到肯定科学结论；
- 通过降低判据制造验收成功；
- 关闭全部历史计划和 pending 条目后才能交付本轮改动。

## 二、目标架构

### 2.1 四个科研工作模块

| 模块 | 负责的完整工作 | 对外主要交付 |
| --- | --- | --- |
| **证据管理** | 获取来源、提取观测、核对条件、保留冲突与不确定性 | 可引用证据及适用边界 |
| **假设与猜想** | 提出竞争解释、预测和反证条件，依据反馈更新候选 | 假设集合及待判别问题 |
| **实验设计与执行** | 科学设计、具体化、实现、开发验证、授权执行与收集 | 实验方案、原始结果和执行记录 |
| **结果分析** | 检查结果有效性、计算比较、评估假设、说明剩余矛盾 | 正式结论、证据、限制与建议 |

四块是**工作组织边界**，不是新的运行时实体。优先复用现有 Operation、工作区和产物。

不新增 `ModuleSpec`、`ModuleRun`、`ResearchEpisode`、模块级第二份 current 或自动科研 DAG。若目录需要展示四个分组，应从现有声明派生，不建立第二份行动注册表；不能用分组替代编译合同或自动选择下一行动。

“证据管理”是一个模块，“证据链”则贯穿全部模块。假设依据、实验实际执行内容和分析来源都必须保留，不是第一阶段做完就结束。

### 2.2 Root 的职责

Root 只承担五类主要工作：

1. 明确总体目标与当前矛盾；
2. 判断缺的是证据、假设、实验还是分析；
3. 选择公开行动及相关材料；
4. 决定投入、转向或停止；
5. 向用户解释进展、限制和风险。

Root 不应长期承担：

- 手动恢复完整来源链；
- 拼装结果读取参数；
- 对照 manifest 搬运文件名；
- 操作普通格式转换；
- 处理完整 spawn／attach 协议；
- 将同一结论改写为下游背景。

Root 仍判断科学相关性，不能把证据选择、研究优先级或停止判断交给确定性程序猜测。

### 2.3 横向控制保持原有权威

| 能力 | 保留的责任 |
| --- | --- |
| Artifact 与来源 | 不可变字节、身份、父链 |
| Run | 工作生命周期、预算、正式交付 |
| 独立审查 | 对精确对象作独立判断 |
| Approval | 人工对精确对象作风险决定 |
| Execution／adapter | 幂等提交、状态、收集、不确定副作用恢复 |

模块合并不意味着 Worker 获得控制面身份、访问未绑定旧工作区或取得额外执行权限。

### 2.4 不是固定流水线

- 有充分证据时，可以直接进入有依据的实验工作；
- 已有实验结果时，可以直接分析；
- 分析发现实现无效，回到实验模块修正；
- 分析发现解释不足，回到假设模块；
- 观测不足，回到证据模块；
- 没有值得继续的问题时，Root 停止。

上述是科学判断的可能分支，不是控制层按 verdict 自动执行的路由表。所有实际调用仍遵守所选 Operation 的编译合同、审查边和审批要求。

## 三、统一判断：什么值得一次 handoff？

每个拟保留的交接都应回答：

> 接手者是否必须作出新的独立判断，或者获得不同权限？

满足以下任一条件，交接有充分理由：

- 需要独立审查；
- 需要人工风险决定；
- 需要改变科学目标、对照或判据；
- 需要另一种专业能力，且当前任务确实不具备；
- 当前任务达到预算或能力边界，需要正式结束并接续。

以下情形通常不值得一次新的模型交接：

- 提取已经存在的计划；
- 展开参数对象；
- 核对已知身份；
- 生成格式化摘要；
- 普通代码纠错；
- 绘图失败后局部重绘；
- 计算完成后让另一个 Agent 重新理解全部输入。

**需要保存记录，不等于需要新任务。**

每个删除或内收候选还需说明：当前生产者、消费者、独立用途、保护的不变量、兼容影响和最小反例。公开入口可能被动态调用，不能以静态搜索没有匹配作为零消费者证明。

## 五、具体工作包

这些是实施分工，不要求每个工作包创建一套计划、单独部署并全面验收。

### 工作包 0：冻结一个可收口的基线

#### 要做什么

只记录以下内容：

- 当前精确工作树候选；
- 哪些改动属于本轮；
- 本轮支持的运行路径；
- 选定的代表场景；
- 对应的已有证据；
- 已知限制与预算。

不重新扫描所有历史运行，不把全部 pending 条目纳入本轮。

#### 交付

一张范围与证据表，附在同一实施记录中。

#### 停止条件

若源码候选、安装版本和证据对应关系无法确定，先解决这个具体问题，不启动新的科研链来猜测安装是否正确。

### 工作包 1：Root 正常路径去操作手册化

这是第一优先级。

#### 1A. 完成结果直接提供决策视图

当前已有 `run_status` 的 `decision` 能力，但仍要求 Root 知道具体字段路径。

修订方向：

- 已知结果类型提供默认的准确字段投影；
- Root 不必手写常见 JSON Pointer；
- 未知类型保留有界导航；
- 全文和细节仍可显式读取。

决策视图按原件实际内容提供：

- 本次任务范围；
- 正式结论；
- 关键限制；
- 剩余矛盾；
- 目标评估；
- Worker 建议；
- 原件入口及遗漏标记。

不能由程序生成新的科学摘要，不能将缺失字段补成“无问题”，不能将 Worker 建议映射为自动行动，不能让视图成为第二份科学结果。只有同次响应确认 completed 后才能使用其科学内容。

主要落点：

- `src/scidiscovery/artifact_agent/interfaces/mcp_root_run_routes.py`；
- `src/scidiscovery/artifact_agent/interfaces/mcp_response_views.py`；
- 对应领域的结果投影声明。

字段选择归属于原结果类型的现有所有者，不在通用核心硬编码所有领域报告。兼容读取与新默认调用规则须显式区分；不存在的字段、null、空值与超限遗漏仍分别表达。

#### 1B. 机械恢复绑定，不替 Root 选择证据

Root 选择要执行的行动、使用的原结果，以及与当前问题相关的进展。

程序负责恢复已选材料所涉及的：

- 精确生产者输入；
- 原始目标；
- 对应审查；
- 必要 manifest；
- 准确实例名称和来源引用。

输出是可确认的绑定候选、确切缺口、歧义和不可用项，不是自动创建研究任务。

保留以下限制：

- 不自动选择最新对象；
- 不按文本相似度猜测目标；
- 不递归绑定全部历史；
- 不把历史可读性当作当前资格；
- 不将可选输入暗中变成必需输入；
- 不自动扩展 Worker 的可见证据或权限。

优先复用已有 `producer_inputs` 和来源查询能力，不新增通用知识图引擎。准入仍由现有完整请求的校验路径决定，准备成功不是资格或资源预留。

#### 1C. 派发机械步骤交给平台适配层

对于 Root 已明确选择并创建的任务，尽量由平台执行：

- 使用冻结模型配置；
- 创建或合法复用 Worker；
- attach；
- 通知打开 assignment；
- 接收完成事件。

权限或平台能力不支持的部分，返回一条明确下一步，而不是要求 Root 重读整份派发指南。平台不得替 Root 选择新的科学 Operation，不得自动换模型、扩大预算或复用作者进行独立审查。

不新增负责读取协议的协调 Agent。

#### 完成标准

正常受支持路径中，Root 不再需要完整读取 `results.md`、`inputs.md`、`dispatch.md` 才能完成一次调度。异常路径仍可查详细说明。

指南依赖只在对应接口和适配路径就绪并部署后撤销，不能先删指令、再让模型猜如何操作。

### 工作包 2：内收确定性中间步骤

#### 优先处理对象

- `science.intake.split.v1`；
- `science.objective.project.v1`；
- `tcad.execution-context.project.v1`；
- `tcad.execution-plan.project.v1`；
- 参数展开与覆盖计算。

#### 修订原则

**先取消 Root 的手工介入，再考虑是否退役独立入口。**

其中有些能力已经是 `support`。仅将目录标签改为 support 不算完成；实际调用和绑定仍由 Root 手工完成，就没有减少交接。

#### 推荐方式

根据具体消费者选择最小方案：

1. 模块内已声明的确定性工具；
2. 已选行动的输入准备步骤；
3. 正式产物的派生视图；
4. 发布时有界生成的附件。

不创建可执行任意工作流的通用编排器。副作用仍由原执行路径负责，不能混进看似只读的准备动作。

#### 特别注意计划投影

`tcad.execution-plan.project.v1` 的产物身份已经被下游核验，不能直接删除它后将嵌套 JSON 当成原来的合格 Artifact。

初期优先：

- 保留原投影对象与来源语义；
- 在受控准备路径中完成机械调用与绑定；
- Root 只处理歧义或真实缺口。

若后续改为消费者直接读取项目内计划，必须一起修改审查、打包和分析的消费合同，不能只改生产者。每个被内收的调用仍须有明确合同、授权和幂等边界，不暗中继承调用者全部权限。

#### 完成标准

减少 Root 的实际调用和绑定步骤，同时原件身份准确、错配被拒绝、旧对象可读，新派生对象不获得额外资格。

### 工作包 3：合并证据模块中的作者任务

#### 首选场景：图证据

当前路径：

```text
图选择 Agent
→ 确定性物化
→ Intake Agent
→ 独立审查
```

目标路径：

```text
一个证据作者任务
  ├─ 定位目标图
  ├─ 调用确定性提取
  ├─ 检查标定、系列身份与缺口
  └─ 交付正式证据
→ 独立审查
```

两个作者环节围绕同一来源和同一提取目标工作，中间主要是确定性计算，具有较明确的合并价值。

#### 必须保留

- 原来源与图像身份；
- 确定性测量记录；
- 曲线与像素的来源关系；
- 不确定性和遮挡信息；
- 完整相关附件；
- 不同 Agent 的独立审查；
- 既有合同要求的资格审批。

#### 实施边界

可能需要调整：

- `plugins/curve_figure_evidence/curve_figure_evidence/figure_science_operations.py`；
- 证据作者的工具声明；
- 工具产物的封存方式；
- 审查输入准备与来源校验。

不能承诺删一个 Operation 就完成。当前物化族身份、完整性和审查输入必须一起闭合。确定性测量仍归原领域算法所有，作者不能手填像素、数值或质量门槛来代替测量。

#### 兼容策略

- 已封存旧图证据不迁移；
- 旧入口是否继续支持新调用，根据真实消费者决定；
- 不用新作者任务的权限重新解释旧 Run；
- 若现有工具证据机制无法表达完整交付，先缩小方案，不增加新的通用工作流状态机。

### 工作包 4：收口实验设计与执行模块

不重做科学骨架。现有骨架、作者内执行计划和综合审查是本批基础。

#### 目标流程

```text
科学骨架
→ 作者连续完成具体方案、源码、开发验证
→ 一次必要的独立综合审查
→ 精确人工执行授权
→ 受控执行与收集
```

这是选定场景的路径，不是所有科研任务必须执行的固定流程。科学歧义、昂贵或不可逆工作仍可需要提前审查。

#### A. 普通工程选择留在作者任务内

包括离散与初始化的具体实现、输出文件安排、开发诊断和局部代码修正。

不能仅因这些选择变化，就自动回到 Root 新建一个设计任务。变化若影响证明对象，旧证明仍须失效并按原合同取得当前证明。

#### B. 科学条件变化必须明确返回

涉及对照含义、科学参数依据、目标、判据、可接受误差与结论范围的变化，必须形成正式变更依据，不能由作者自行降低要求。

#### C. 独立审查直接消费完整项目

不经由 Root 重写作者说明。审查者取得骨架、具体计划、源码、当前诊断、关键原始输出和未验证范围。

开发诊断要能回答当前实现有效性问题；退出码成功、文件存在或初始化成功不能替代关键动态行为证据。

#### D. 独立核验证明退出正常流程

对于 `tcad.deck-review-validate.v1`：保留真正消费位置的核验函数，不把单独生成证明作为普通必经步骤；独立入口退役取决于对外兼容需求。

#### 不能合并的权力

模块内部工作连续，不等于作者可以：

- 审查自己的项目；
- 代替人工批准；
- 通过原生 shell 执行生产求解；
- 将开发诊断当正式实验结果；
- 自动扩大诊断预算或改名延续相同失败。

新骨架路径的支持范围以当前合同为准，不能将受支持的 SProcess 路径外推为 SDevice 已完成适配。

### 工作包 5：收敛结果分析入口

#### 默认行为

一次分析任务内部完成：

```text
读取原始结果
→ 判断执行有效性
→ 按需计算／评分
→ 按需作图
→ 科学解释
→ 正式交付
```

不要求 Root 将计算、绘图和解释拆成多个阶段。

#### 现有入口的处理

- `tcad.result.analyze.v1` 保留为 TCAD 正常分析入口；
- 通用分析保留领域无关的正常入口；
- 固定预计算包解释作为有明确用途的专用路径保留；
- 独立误差分析 Transform 作为算法能力保留，不默认安排为前置阶段。

#### 不做错误合并

通用分析与 TCAD 分析具有不同来源关系和工具权限，不能只因都输出 LayeredDiagnosis 就合成一个大入口。

目标是普通用户只需选择适合实际结果来源的分析方式，不是让所有底层能力只有一个函数。固定预计算解释仍可用于不允许重算、复用已有计算或限定权限的任务。

#### 恢复要求

- 数值结果先保存，再处理可选绘图；
- 绘图失败不导致整批计算重做；
- 失败保全不继承科学资格；
- 正式提交不重复执行已有可信记录的计算；
- 下一轮直接引用原件，不重新生成背景报告；
- 实现或数值失败不被解释为物理反证；
- 停止工作不将 inconclusive 改写成科学否定。

### 工作包 6：清理重复运输和旧协议

在前述路径稳定后完成，避免先做表面清理。

#### A. handoff 单一内容所有权

逐类处理，不全局删除：

- 正文已有正式结论时，handoff 只引用或机械投影；
- 正文没有整体说明时，保留唯一科学总述；
- 机械状态由控制层生成；
- 已有显式说明不能静默丢弃。

不为统一格式新增总报告，不把 SchedulerSignal 变成新的科学权威，也不删除当前已实现的自动物化机制再重做一遍。

#### B. 退役废弃路由字段

优先从新写入和模型可见面移除 `accepts_actions`、`next_action_kind`。旧记录仍可解析，编译身份变化显式处理；不改写旧 Artifact 或在途 Run。

#### C. 指南退出正常前置路径

分为三层：

1. **Root 常驻短原则：**科学决策与权力边界；
2. **所选行动短合同：**当前调用真正需要的信息；
3. **异常参考文档：**兼容、恢复、安装和特殊诊断。

同步修改 `roles/scheduler.md`、对应分指南、平台生成逻辑、安装校验和双语架构说明。不能只删提示词，而让原复杂调用协议保持不变。

## 六、迁移与兼容策略

### 6.1 不改写历史

保留已封存 Artifact 字节、原父链、原 Run 终态、原审批以及原失败和验收记录。

### 6.2 新旧合同不混用

- 已打开任务继续使用原冻结合同；
- 新部署不能热替换在途 assignment；
- 新项目不继承旧审查；
- 输出科学含义不兼容时，按现有机制提升版本；
- 字段看起来一样不能证明来源或资格相同；
- 历史读取、当前审查资格、Run 恢复和外部执行分别遵守各自身份边界。

### 6.3 先减少默认暴露，再退役入口

退役分两步：

1. 正常任务不再需要该入口；
2. 确认受支持消费者及迁移方式后，才停止新调用。

静态搜索只能提供线索，不能证明外部客户端没有使用公开入口。保留旧 reader 不等于必须保留所有旧 writer；两者应分别论证。

### 6.4 回退候选，不回退科学历史

出现问题时：

- 停止新任务；
- 保留失败现场；
- 按现有发布机制回到已知候选；
- 不删除新产生的科学记录来制造干净状态；
- 不重开已关闭的无关部署改造支线。

本计划不新增发布事务或状态回滚系统，不承诺未经验证的数据降级兼容。

## 七、验收策略：证明更少交接，而不只是还能运行

### 7.1 三个代表场景

#### 场景 A：读取既有结果并选择下一步

不运行新 solver，验证：

- Root 无需完整步骤指南；
- 能取得正式结论、限制和矛盾；
- 能恢复所选下一行动的必要原件；
- 不把建议当自动命令。

用于工作包 1、2。机械恢复可用隔离环境验证；现场原件只通过现有受控接口读取，不用数据库直读代替真实入口。

#### 场景 B：一次完整图证据提取

使用冻结来源，验证：

- 同一作者完成定位、工具提取和证据整理；
- 独立审查者收到完整必要原件；
- 不伪造标定、缺失或不确定性；
- 减少作者之间的上下文重建。

用于工作包 3。图像、目标和判定依据事前冻结，不在看到结果后挑选容易通过的材料。

#### 场景 C：受支持的最小 SProcess 工作

验证：

- 作者连续完成实现和开发检查；
- 独立综合审查不依赖作者聊天；
- 执行经过原有精确批准；
- 结果能被正式分析；
- Root 能继续或停止。

用于工作包 4、5。不把 Fig.4 机制识别成功作为框架通过条件。

场景开始前必须确定科学问题、预期可观察行为、判据依据、必要输出、真实 capability、预算和停止条件。由适当科学设计与独立审查确定这些内容，工程计划不编造物理参数。无可用执行能力或未获批准时记为未执行／阻断，不能用模拟适配器宣称现场通过。

### 7.2 每个场景同时覆盖三个维度

| 维度 | 要确认什么 |
| --- | --- |
| 正向能力 | 约定的正常任务确实完成 |
| 边界保护 | 错对象、旧证明、未批准执行仍被拒绝 |
| 简化收益 | Root 介入、上下文重建或重复填报确实减少 |

规范地返回 blocked 可以证明失败分支正确，不能代替正常主链完成。

可用既有可核验材料回放伪成功场景：退出码成功、文件齐全，但关键行为未生效时，不得误判有效实现。优先复用已有失败证据，不为验收重新执行已知无价值的求解。

### 7.3 衡量什么

事前冻结同一任务范围，记录：

- Root 的机械调用次数；
- 必须阅读的协议说明；
- Agent 交接及上下文重建次数；
- 重复填报和重复读取；
- 人工修补绑定的次数；
- 从输入到正式决定的时间；
- 实际可观测的 token；
- 错误结论、漏交证据和越权情况。

不预设无依据的百分比收益。没有原生 token 记录时写不可观测，不从字节、耗时或代理会话推算。

若只减少文件数、没有减少实际交接，不能称为结构性收简成功。减少交接也不能掩盖科学质量或安全边界退化。单次行为通过不证明开放研究的统计可靠性。

### 7.4 验证范围与资源纪律

- 根据精确 diff 选择直接检查、生产者—消费者组合、对应负控和实际安装入口验证；
- 复用足够且适用于当前候选的证据，不因旧计划未全部关闭就重跑上游；
- 触及广泛共享合同或核心生命周期时才扩大回归范围；
- 串行运行，不让重测试与 solver 同时争用资源；
- 进程树采样守卫不等于硬内存隔离；
- 无法保证资源边界时，不在原先发生崩溃的环境继续扩大检查；
- 预算和执行授权另行明确，不因本计划而提高现有上限。

本文件当前不授权运行这些检查。

## 八、实施顺序：分批交付，不无限扩大

### 第一批：先解放 Root

范围：决策视图、机械绑定恢复、少量最常用投影内收，以及对应指南与安装合同同步。

不同时修改 solver、全部证据 Schema 或所有分析入口。通过后即可形成独立可用的收简成果，不等待整个战略完成。

### 第二批：合并图证据作者工作

只处理一条证据生产路径，保持独立审查和资格边界。若合并没有降低交接，或引入过多新合同，停止扩展并重新判断切口。

### 第三批：收口实验与分析的连续工作

基于已有骨架、作者工作区和分析工具修复具体断点，不重建整套科学对象。

### 第四批：退役旧表面

最后处理不再必要的独立入口、废弃字段、失去用途的指南和过时默认路线，避免在新路径尚未证明可用时先拆掉旧路径。

上述批次是工程交付顺序，不是新增科研阶段。每批保持精确范围和独立复核，避免给每个小补丁另开一套全面计划、部署和审查。

## 九、审查与返工规则

### 9.1 每条阻断必须说明

1. 可达场景；
2. 违反的冻结要求；
3. 具体证据；
4. 最小修复；
5. 可观察的关闭条件。

“可以更严谨”“最好再多覆盖一些”不能单独成为阻断。

### 9.2 必须阻断

- 科学结论与关键证据矛盾；
- 约定正例没有完成；
- 来源或审查错配；
- 权限、审批、不可变性被绕过；
- 关键证据无法交接；
- 超出冻结预算；
- 外部副作用状态不明却继续盲目提交。

### 9.3 通常不阻断

- 尚未证明普遍性能优势；
- 另一个平台未覆盖；
- 文案、排版或抽象方式可以更好；
- 本场景不使用的历史入口尚未退役。

严重安全问题不能因不在范围而忽略，但应停止受影响发布并明确处理范围，不能将整个项目再次扩成无限整改。

独立计划审查、工程复核和科学对象审查各有职责，不能互相替代。改变内容后必须获得适用于新候选的结论，不继承旧 verdict；复核关注受影响部分及其组合边界，不无依据重开所有已闭合事项。

### 9.4 返工封顶

建议每批采用：

> 首轮验收，加一次有实质修复的复验。

仍失败则明确结束该批，保留成果与失败原因，决定缩小支持范围或单列能力缺口。

不换名称继续同一尝试，不自动扩预算，不追改标准以取得通过。该上限是拟议的工程收口规则，不修改已有 Run 的尝试次数、恢复规则或外部审批预算。

## 十、工程与文档纪律

避免修订本身继续制造臃肿：

- 一个总计划；
- 一份持续追加的实施记录；
- 每批对应的精确独立审查和验收证据；
- 一个当前入口；
- 不为每个小修再开一整套计划。

代码方面：

- 优先修改现有职责所有者；
- 不新增通用编排框架；
- 不用复杂配置语言替代几个确定性函数；
- 不因字段重复就合并职责不同的类型；
- 不将全量测试数量当作收简收益；
- 只运行与精确改动及其消费者相关的检查，必要时才扩大范围；
- 不为了减少行数删除实际保护来源、权限和副作用的检查；
- 先删除重复责任，再考虑文件拆分和 helper 抽象。

文档方面：

- 当前规范与策略提案分开；
- 不用索引文字覆盖精确审查记录；
- 更新受影响的双语规范段落，但不将整个历史语料重写为当前状态；
- 每次范围承接只注明实际承接项，不让“最新计划”自动继承所有旧待办；
- 不把文档整理或所有历史链接清理作为科学恢复的额外前置门。

## 十二、首批建议与当前状态

**先做第一批，不同时启动全部重组。**

最优先的三个动作：

1. 让 Root 直接取得可决策的正式结果，而不是读操作手册；
2. 将精确绑定和确定性投影交回程序；
3. 让同一作者的连续工作不再被拆成多次交接。

四块架构的价值不在数字“四”，而在以下原则：

> **只有新的科学判断、独立责任或权限变化，才值得形成新的交接；其余工作尽量在原任务或确定性程序内部完成。**

当前仅将策略写入文档并增加索引。未进行本策略的独立审查、源码实施、测试、模型运行、部署或科研执行；现有安装、科学结论和审批状态不因本文变化。
