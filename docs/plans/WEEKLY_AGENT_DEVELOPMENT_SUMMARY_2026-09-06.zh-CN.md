## 1. 本周总体进展

本周完成的核心变化，是把框架从“分散注册的流程控制器”收敛为：

```text
插件定义
  → OperationSpec 行为声明
  → 安装期统一编译
  → 唯一操作目录
  → 预检
  → 调用
  → 智能体／确定性变换／审批／外部执行
  → 封存结果
```

同时完成了论文曲线提取插件的真实验证：智能体负责读图、坐标标定和曲线身份判断，程序负责像素提取、数值还原、统计、共享像素与文件生成；真实 Fig.4 已在安装态子智能体中跑通。

## 2. OperationSpec 的设计机制

### 2.1 基本定位

`OperationSpec` 是整个系统的基本行为原子，可以理解为一个“可编译的行为闭包声明”。

它不是包含全部逻辑的巨型类。它只声明：

- 这个行为是什么；
- 什么情况下适用、不适用于什么；
- 消费哪些输入；
- 产生哪些输出；
- 由哪类执行器运行；
- 可以使用哪些领域工具；
- 允许看到哪些上下文；
- 有什么资源限制；
- 是否需要独立审查、人工审批或外部副作用授权。

具体实现由插件中的窄组件提供，例如：

- 数据编码器；
- JSON Schema 资源；
- 内容校验器；
- 跨输入校验器；
- 准入守卫；
- 智能体提示；
- 智能体领域工具；
- 确定性变换函数；
- 审批内容投影器；
- 外部执行适配器；
- 工作区钩子。

因此关系是：

```text
OperationSpec
  ├── 输入/输出合同
  ├── 执行器引用
  ├── 工具与权限声明
  ├── 资源限制
  ├── 审查/审批声明
  └── 窄组件引用
          ├── 提示
          ├── Schema
          ├── 校验器
          ├── 工具实现
          └── 确定性代码
```

### 2.2 四种执行形式

同一套 `OperationSpec` 支持四种执行闭包：

| 类型 | 职责 |
| --- | --- |
| 智能体操作 | 开放式科学判断、代码编写、实验设计、证据解释 |
| 确定性变换 | 可重放的机械计算、格式转换、打包、评分 |
| 审批操作 | 将精确对象投影为人工审批页面 |
| 副作用操作 | 创建外部执行请求，例如真实 TCAD 求解 |

它们共享同一个操作目录、预检入口和调用入口，没有平行注册体系。

### 2.3 三种目录视图

操作本身声明所属范围：

- `public`：调度智能体可以选择的科学行为；
- `support`：某个公开行为需要的确定性辅助操作；
- `internal`：框架测试和内部自检操作；
- `all`：前三者的诊断联合视图。

这些是同一编译目录的不同投影，不是多个注册表。

### 2.4 为什么称为行为闭包

安装编译后，一个操作会得到：

- 完整组件引用闭包；
- 输入输出合同；
- 工作区和工具权限模板；
- 审查边和审批提供者；
- 网络与资源限制；
- 所有静态资源摘要；
- 唯一操作摘要；
- 对应的 Codex 子智能体类型。

任意组件、提示、Schema、插件版本、工具声明或审查者发生变化，操作摘要都会变化。旧运行结果不会伪装成新合同下的结果。

## 3. 新插件接入后的运行逻辑

### 3.1 调度阶段

调度智能体只从统一编译目录中选择公开操作，然后绑定当前研究实例中的精确语义对象名称。

例如：

```text
science.figure.request.prepare.v1

paper_source       → ingaas_inalas_fig4_source_paper
research_objective → 可选的研究目标
```

绑定完成后必须先执行预检。

### 3.2 预检做什么

`operation_preflight` 是只读检查，不创建运行、不执行智能体、不产生科学对象。

它主要检查：

1. 操作是否存在于当前编译目录并可供当前后端执行；
2. 输入是否属于当前研究实例；
3. 输入端口名称是否完整且没有未知端口；
4. 每个端口的数量是否满足上下限；
5. Schema、媒体类型和单文件大小是否匹配；
6. 同一对象是否被重复绑定；
7. 总输入大小是否超限；
8. 要求当前版本的输入是否确实为当前对象；
9. 可选输入组是否满足“全部存在或全部缺失”；
10. 必需的顶层字段是否非空；
11. 插件声明的父链守卫是否通过；
12. 生产者、完整输出族、独立审查和资格关系是否匹配；
13. 智能体所需领域工具和运行服务是否可用；
14. 恢复请求是否绑定同一操作摘要、同一输入和合法重试次数；
15. 审批或副作用合同是否能够投影；
16. 操作名称和不可变调用指纹是否存在冲突。

预检成功只授权对完全相同的请求执行调用。不能改完输入后沿用之前的预检结论。

预检判断的是“这次精确调用现在能不能创建”，而不是科学结论是否正确。

### 3.3 调用做什么

`operation_invoke` 会在创建锁内重新执行同一套检查，避免预检后对象、资格或审批状态发生变化，然后根据执行器类型分流。

#### 智能体操作

```text
invoke
  → 创建 queued Run
  → 冻结操作摘要、输入、指令和角色类型
  → 返回由操作摘要生成的 agent_type
  → 父调度器启动无父历史的子智能体
  → 子智能体打开 assignment
  → 读取显式输入并调用声明工具
  → 写入结果
  → JSON Schema 校验
  → 少量语义规则校验
  → 上下文绑定校验
  → 封存输出并登记不可变 Artifact
```

父智能体不能把子智能体聊天当作科学结果，只有 `run_status` 中的封存输出才有效。

#### 确定性变换

立即读取精确输入字节，调用已编译函数，校验每个输出端口，然后一次登记全部不可变结果。

#### 审批操作

根据插件投影器生成固定安全审批文档，创建待处理审批并返回回环页面地址。对话文字不能代替页面决定。

#### 副作用操作

创建精确外部执行请求和对应审批，但不会自行批准或启动执行。人工批准后才允许进入外部执行生命周期。

## 4. 安装和编译时发生了什么

### 4.1 选择插件

安装器读取 `SCID_PLUGINS`，例如：

```text
tcad_artifact,curve_score,curve_figure_evidence
```

然后检查：

- 插件目录和 `pyproject.toml`；
- 发行包名称；
- 插件依赖是否一起安装；
- 是否存在重复插件；
- 是否引用未知插件。

### 4.2 构建隔离安装包

核心包和选中的插件被复制到临时构建区，再离线构建并安装到新的安装暂存目录。未选择的插件不会进入生产安装态。

### 4.3 从唯一入口发现插件

每个插件只发布一个统一入口：

```toml
[project.entry-points."scidiscovery.plugins"]
curve_figure_evidence = "curve_figure_evidence.plugin:PLUGIN"
```

入口返回一个 `PluginDefinition`，其中包含：

- 插件编号和版本；
- 插件依赖；
- 全部组件；
- 全部操作；
- 可选运行时配置与运行工厂。

### 4.4 编译唯一操作目录

编译器一次性完成：

- 插件协议和版本校验；
- 插件依赖校验；
- 组件实现导入及类型检查；
- 跨插件引用权限检查；
- Schema 编号与资源内容检查；
- 输入输出端口检查；
- JSON Schema 与语义规则绑定检查；
- 校验器与规则编号绑定检查；
- 工具名称、参数模型和服务依赖检查；
- 网络权限与网络工具一致性检查；
- 独立审查边检查；
- 审批提供者检查；
- 修订合同检查；
- 未使用私有组件检查；
- 资源上限自洽检查。

随后生成唯一 `CompiledCatalog` 和每个操作的摘要。

这里不会让智能体实时编译操作，也不会自动生成任意科学校验代码。它做的是将声明好的 Schema、语义规则、校验器、工具和执行器解析并冻结成唯一运行合同。

### 4.5 生成 Codex 配置

每个可执行智能体操作都会生成：

- 唯一 `agent_type`；
- 对应角色配置文件；
- 编译后的专家提示；
- 模型设置；
- 工作区说明；
- 原生工具授权说明；
- 专属 Worker MCP；
- 允许调用的领域工具清单；
- 打开任务、心跳和提交结果三个生命周期工具。

`agent_type` 包含操作摘要片段，例如：

```text
op_science_figure_request_prepare_v1_ed23fbcb0df6
```

因此不同版本的同名操作不会混用角色配置。

安装器还会生成根调度 MCP、调度规则 `AGENTS.md`、源码目录/项目工作区/实际 Codex 启动目录的配置、systemd 服务和运行时身份清单。

最后启动服务并验证：

- 根 MCP 是否只有当前操作入口；
- 编译目录是否能重新加载；
- Worker 工具是否齐全；
- 审批页面是否可访问；
- 插件依赖是否与安装时冻结值一致。

安装完成后必须重启 Codex，新的角色和 MCP 配置才会生效。

## 5. 当前方案的主要价值

### 5.1 通用与专业实现真正分离

核心不需要理解 TCAD Deck、曲线像素、论文图号、器件参数、求解器命令或领域审查格式。这些内容全部由插件通过操作和组件声明接入。

### 5.2 插件不再需要修改多张注册表

新增领域能力的理想路径变成：

```text
实现领域组件
  → 声明 OperationSpec
  → 加入 PluginDefinition
  → 通过唯一入口安装
  → 自动编译目录、角色、工具和运行合同
```

不再分别修改角色表、调度表、工具表、准入表、页面表和执行表。

### 5.3 保留多智能体分工，但不固定科研流程

调度智能体根据当前问题选择操作，依赖只表达数据准备条件，不表达固定阶段顺序。

因此仍可保留提出者与审查者、证据提取与证据审查、假设提出与批判、实验设计与代码审查之间的职责分离，但不会把科研过程硬编码成不可改变的工作流图。

### 5.4 上下文和能力按操作收敛

子智能体只获得当前任务指令、声明的输入文件、输出合同、当前操作的领域工具和当前工作区。

领域工具由服务端按操作限制。当前本地版本对 Codex 原生文件能力采用软隔离，这是为了快速闭环，不应被描述成操作系统级强沙箱。

### 5.5 控制面回归合理职责

控制面主要负责精确身份、不可变输入输出、基本合同校验、Run 生命周期、独立审查绑定、人工审批、外部副作用授权以及失败和恢复记录。

它不再替智能体判断科学内容，也不再依靠大量经验阈值阻止科研工作。

### 5.6 本周图像插件验证了这套边界

新的曲线提取链为：

```text
智能体：
  看原图
  → 判断图框、刻度、曲线身份
  → 调用预览
  → 查看原图叠加图和数值重绘图
  → 自行修订并提交

确定性程序：
  取真实像素
  → 坐标还原
  → 计算点数、范围、缺口和共享像素
  → 生成 CSV、清单、报告和两张审阅图
```

真实 Fig.4 已完成安装态子智能体验收；OCR、自动识轴、自动图框、经验点数阈值等不可靠路径已经退出主链。

## 6. 新开发一个 Operation 需要做什么

### 6.1 明确行为边界

先写清楚：

- `purpose`：它解决什么问题；
- `applies_when`：什么时候应该调用；
- `not_for`：哪些事情不属于它；
- 它是智能体、确定性变换、审批还是副作用操作；
- 它应该属于 `public`、`support` 还是 `internal`。

一个操作最好只对应一个明确科学职责。

### 6.2 定义输入输出合同

为每个输入端口声明：

- 端口名称；
- Schema；
- 媒体类型；
- 最少和最多数量；
- 单项大小；
- 上下文暴露方式；
- 科学用途；
- 是否必须是当前对象；
- 真正必需的非空字段。

为每个输出端口声明：

- 对象种类；
- Schema；
- 媒体类型；
- 数量和大小；
- 内容校验器；
- 上下文校验器；
- 校验器允许读取的输入；
- 是否为多文件集合。

### 6.3 准备最少的组件

智能体操作通常需要：

- 一个提示资源；
- 一个智能体组件；
- 工作区组件；
- 输出 Schema 资源；
- 内容校验器；
- 少量跨字段语义规则；
- 必要的领域工具。

确定性操作通常需要变换函数、输入输出 Schema 和输出校验器。

审批操作需要审批对象投影器以及问题、选项和精确审批对象声明。

副作用操作需要副作用准备器、运行时工厂、外部适配器和人工审批合同。

### 6.4 注册工具

如果智能体需要领域能力，要实现一个窄工具：

- 工具名称；
- 简洁说明；
- Pydantic 输入模型；
- 处理函数；
- 所需外部服务；
- 是否需要网络。

然后把该工具组件引用加入对应 `OperationSpec`。

工具应当完成有价值的确定性工作，例如调用 TCAD 调试后端、恢复 PDF 嵌入图、提取曲线像素、计算评分或解析求解器输出。

不应让智能体手工填写程序能够计算的点数、范围、摘要或 CSV。

### 6.5 声明审查和审批

只有真正需要时才增加：

- 独立审查边；
- 最大修订次数；
- 修订进度指纹；
- 人工审批；
- 资格输入组；
- 完整变换输出族。

普通操作不要默认附加全套治理结构。

### 6.6 加入插件定义

把新增组件和操作加入插件的唯一 `PluginDefinition`。

如果是在已有插件中新增操作，不需要增加新的入口。只有创建全新插件时，才需要新插件目录、`pyproject.toml`、一个 `scidiscovery.plugins` 入口和插件依赖声明。

### 6.7 完成最小测试

至少需要验证：

1. 插件可独立编译；
2. 与必要依赖组合安装时可编译；
3. 公开目录中出现正确投影；
4. 正确输入通过预检；
5. 错误 Schema、数量、父链或资格被预检拒绝；
6. `invoke` 与预检使用同一判定；
7. 智能体实际能打开任务；
8. 智能体实际能调用声明的领域工具；
9. 输出 Schema 与提交校验器一致；
10. 真实子智能体能成功提交一次；
11. 确定性变换可重复产生相同结果；
12. 安装后的包运行结果与源码测试一致。

### 6.8 安装并重启 Codex

在 `SCID_PLUGINS` 中选择新插件，执行安装器。安装完成后重启 Codex，新的智能体类型、MCP 和工具配置才会生效。

新增一个操作的最小开发面可以概括为：

> 定义输入输出，复用或实现窄组件，声明一个 OperationSpec，加入一个插件入口，完成预检、调用、工具和真实智能体验证；不需要修改核心调度器。

## 7. 当前仍需保留的边界说明

- 默认本地后端采用软隔离，不是操作系统级强沙箱；
- 当前 Agent Run 只支持一个主结果，确定性变换可以输出多个对象；
- 审批页面的信息层级和视觉可读性仍需后续改进；
- 当前已经证明架构边界和 TCAD／论文图最小纵向能力，不等于已经通过多领域统计性通用能力评估。
