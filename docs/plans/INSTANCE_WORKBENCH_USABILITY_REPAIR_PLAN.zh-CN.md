## 已发生的问题与判定

用户现场反馈：缺少层次、滚动条极长、英文与机械字段堆积，不能有效阅读或审批。
实际 Chromium 证据保存于 `evidence/instance-workbench/FIG4_LIVE_DETAIL_CHECK.json`：
最新节点页面高18,111像素，约30,114字符；资格审批节点高15,694像素。
HTTP正常、无JS异常、窄屏不溢出，只能证明基本运行，不能证明界面可用。

同时复现两个内容选择缺陷：

1. 精确最新 `fig4_user_context_continuation_review_1` 正式 `/verdict` 为 pass，页面却未展示其正式摘要，
   先展示作为背景输入的旧实现审查 blocked。原因包含输入先于当前输出进入有界父链读取，及提供者拼接顺序。
2. 目标沿所有祖先泛搜，同 schema 背景计划被当成原计划竞争者；虽已发现同一原目标，概览仍清空目标显示。
   应优先使用现有精确 producer Run 输入端口及 materialized plan→intent 关系，不按 schema 匹配替代版本绑定。

本轮现场可用性不通过。原独立工程 PASS 保留为历史，不扩写成现场 PASS。

## 实施步骤

### U1 正确区分本节点成果与背景

- 在现有节点读取投影中标明本节点精确成果与输入/历史背景；先为本节点成果保留读取与呈现预算。
  完成Run只用自身output作为本节点结论；失败Run明确没有封存结果，不把输入中的审查当作自身结果。
  这项优先级须贯穿父链读取、提供者拼接和最终HTML三个预算，不能只交换读取队列顺序。
- 当前成果、当前任务/计划、历史依据分开显示。保持每项原Artifact+JSON Pointer来源；未知/超限留可读入口。
- 审批以原请求的精确subjects与既有决定组织“审批事项/允许动作/依据/缺口”，历史已决定请求仅展示原决定。
  不为了展示生成或刷新审批决定，只有原审批入口拥有决定表单。
- 原目标读取优先原绑定：Run objective→所绑定计划的原设计/修订链→确切producer输入端口。
  background/current_progress同schema记录不能抢占原目标；仍然无法唯一定位时保留多个来源与缺口，不能猜选。
  不将UI导航用作新的科研准入。

### U2 重排信息层级和视觉布局

- 实例首页：紧凑标题和状态区、原研究目标、当前/最近节点结论卡、可点击的阶段/节点轨迹。
  阶段是已有节点类型的展示分组，不声称固定科研顺序；多个分支分别保留，不合成总体成功。
- 默认轨迹突出Run、审查、审批和执行；机械Artifact登记归入明确的“全部记录”入口。
  保留原分页游标与下一页，不因过滤把历史隐藏且无入口。时间、人类可读节点类型与状态为主，内部名称放详情。
- 节点详情分成“概览 / 参数与图表 / 依据与日志”。默认只展开概览，其余可按需打开。
  中文状态徽标区分运行完成、科学结论、审批决定；一份节点成果只作为主结论出现一次。
- 审批页顶部先回答“批准什么、允许什么、主要依据和未解缺口”，桌面保留紧凑决定栏；手机先依据后决定。
  参数、图件和长依据按区块进入；原表单字段、过期刷新及决定身份保持不变。
- 参数表使用紧凑列与行详情，选值、单位、来源类型及不确定/默认标记可直接看到；报告值、条件与长引用按需展开。
  图件用缩略图/并列图卡和明确原件入口，实际图加载后检查，不能把懒加载未触发当成坏图。
- 中文化界面标签、状态、节点类型、已知枚举、按钮与时间表达。仅有英文的科学叙述标为“报告原文（英文）”并折叠，
  不自动翻译或改写科学内容；用原中文目标和可确定的中文状态/结构化关键项建立首屏层次。
  原文、原始字段和精确引用仍可查阅，不用满页JSON或英语字段名承担默认导航。
- 使用既有HTML/CSS/少量JS；无JS时原生链接和details仍可打开，审批表单始终可操作。推送只提示元数据变化。

### U3 用真实页面形状验收，再独立复审

- 从本次授权只读UI取得必要的真实节点投影/原件，保留精确来源；隔离展示服务器重放，不读取生产数据库。
  不启动科学Run、外部执行、审批决定或真实归档。浏览器拦截所有非读取请求，隔离表单测试除外。
- 核对最新审查pass和旧实现blocked同时存在时，主卡只显示最新节点自身结果；失败节点不借用输入结果。
  单一原目标、同schema背景计划与多目标歧义分别检查；不增加科学校验。
- 真实长页面在1280×900下，默认节点页高度目标≤2,400像素，并至少较18,111像素旧页减少80%；
  参数/图件能一次点击进入，原文与日志仍完整可定位。390像素宽度不横向溢出，手机依据在决定之前。
- 核对两类真实历史审批、当前审查、失败节点、参数表、已加载图件与轨迹截图；逐张人工检查信息层次，
  不再以HTTP200或DOM中存在字段作为可用性PASS。旧历史缺失与不支持项明确记录。
  历史已决定审批使用原request/decision的只读展示；另以隔离pending请求验证原审批表单与手机布局。
  两者分别记录，不把普通approval节点截图称为原决定表单已验收。日志按实际events读取，并核对分页及原错误入口。
- 定向原审批身份/权限、展示、诊断分页、推送回归；同环境45/50合同快照保持。测试、构建、浏览器串行，
  单进程树512MiB预算，不跑全量套件，不并行测试。
- 先独立审查本计划的功能完整性与框架边界；必要修订后复审至通过，再实施。完成后独立实现复审，
  交付前提供真实长度材料的截图、默认高度变化、遗留缺口和是否需要重新安装。

原R3计划与PASS不回写；本修订和现场失败另立记录。未完成真实可用性检查不得再报告工作台已验收通过。
