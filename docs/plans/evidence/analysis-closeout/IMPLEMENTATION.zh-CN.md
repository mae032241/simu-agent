# 三项收尾实施记录

2026-09-12。用户授权把三个收尾点修复或验证。基于本轮开始时已有大量改动的工作树保存独立 baseline，增量为六个既有生产文件及两个所属测试文件。未改科学 Schema、Operation 端口、审批、VM runner、Run 四态或科学提交门槛。

## 改动与依据

1. **可选路径准确。** 共享分析入口直接使用恢复覆盖的实际可用性；无草稿、旧草稿没有覆盖清单、没有历史运行目录时，对应路径为 null。现有草稿仍可恢复可编辑工作副本。
2. **原生命令错误可见。** 原有本地分析启动器增加 argv 命令模式，供 Worker 在原权限范围内执行准备/读取/诊断命令；原 Python 脚本模式保留。共用原有时间、内存、进程组和日志上限，不采用 shell=True。最近记录累计已观测命令数、输出字节数及最多八项错误；成功命令不擦除之前失败。Root run_status 的诊断摘要显示最近原生错误类型、退出状态和日志相对指针，不输出命令内容或未封存科学正文。旧启动器记录仍能反映已知的最近失败。没有观测不等于没有错误，直接绕过启动器的平台调用仍不在其覆盖内。
3. **现场恢复缺口。** 第一项真实恢复任务在打开阶段失败，尚未进入分析或提交。代码复现证明：原逻辑把当前未绑定旧证据依赖与原收据不一致合并为 integrity_failure；输入重排后，多次恢复还可能按中间 Run 的别名误解原记录。现已按原注册 producer 核实来源；有效但不适用于本轮输入的旧产物保留为草稿，不自动纳入本轮工具证据。Root 和 Worker 使用同一函数展示原保存数、已采用数和未采用记录索引。真正损坏的字节和错误来源仍拒绝，后者能定位 records[i]。
