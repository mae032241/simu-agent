## R1 — P1：单槽后台收集与不可停止的兼容调用存在冲突

计划位置：P2 第4、5、7项（103—106行），P3 第7、8项（141—142行）。

计划规定 daemon 默认只运行一个收集任务，工作者确认停止后才能释放锁；同时允许旧 `collect(external_run_id)` 在后台运行，不能停止时持续占锁。这里尚未选定具体可停止的执行单元，“线程/子进程”不能作为等价的实施选择。

可达后果：旧适配器的 collect 若不返回，在线程实现下无法仅凭600秒预算停止调用；它可能持续占有唯一工作槽，后续其他执行也无法收集。将细项标为 unsupported 或将记录写为 timed_out，并不能证明工作者已经结束。新实现若把收集与登记都放在同一线程，也不能仅靠终止 SSH 子进程保证整段工作已经停止。

当前 `ExecutionAdapter.collect` 没有停止或预算参数；`ExecutionService.ingest_result` 同步登记多个 Artifact 后才提交执行终态。这说明“传输停止”和“登记停止”需要明确不同的安全边界。

最小修订要求：

1. 选定本版实际采用的执行方式，写明到期后的停止、回收、锁及工作槽释放顺序；不能仅取消 Future 或修改状态文件。
2. 明确兼容调用的受控执行边界，不能让一个不可停止的旧调用无限占用全局唯一收集槽，同时继续声称整次收集有界。
3. 规定工作槽忙时的返回行为，避免无意引入无界待执行队列。查询、重复请求不得增加后台工作。
4. 区分传输取消与登记的安全恢复点，保留计划已有的稳定 manifest/collected_at 幂等设计；不得在数据库提交过程中用粗暴中断替代恢复规则。

验收补充：用短时受控故障模拟不返回的收集调用，证明实际工作者被回收、之后另一执行可收集、服务停止有界；登记边界故障后不产生重复结果。无需等待真实600秒。

## R2 — P1：预算传递接口尚未落定，作者调试的实际调用点遗漏

计划位置：P3 主要位置及第1、2、8、9项（116—143行）。

计划要求“明确的可选扩展”接收预算和进度，但没有给出扩展的调用合同、跨 command/socket 的传递方式，以及剩余预算在哪里计算。对作者调试与分析恢复仍使用“必要时局部适配”的表述。

源码中有明确的受影响调用：

- `local_debug_service.py:122` 在终态直接同步调用 `self.adapter.collect(...)`，该调用没有传递当前 Run 剩余时间；启动阶段137行的预算裁剪不能约束后续收集。
- `debug_adapter.py:405` 及 `debug_contract.py` 的 collect 接口只传外部执行标识。
- `command_adapter.py:209` 调用通用 `_call`，258行仍使用统一 `operation_timeout_seconds`。
- `output_recovery.py` 通过适配器现有 timeout/config 属性裁剪工具预算；新增收集预算后，需要明确它是否仍被正确消费。

因此，只完成 Root 的异步收集入口，不能证明作者调试不再遇到旧短超时；若直接让通用 collect 改用600秒，又可能突破作者或分析 Run 的剩余时间。

最小修订要求：

1. 在计划中落定一个具体的预算/进度扩展合同：参数、消费方、进度传递位置及终止结果。明确旧调用的默认行为，避免各适配器自行解释。
2. 将 `local_debug_service.py`、`debug_contract.py` 列入确切适配范围；在调试收集的实际入口计算剩余授权时间并传递。分析恢复也应核对其真实消费路径。
3. 根层收集总预算、Run 剩余预算与各子步骤预算统一按剩余时间裁剪；连接解析、建连、下载等步骤不能各自重新获得一整份总预算。
4. command、socket、SSH 及公开工具 Schema 使用同一默认值与参数含义。进度应从实际执行路径产生，不能只在 Root 增加展示字段。

验收补充：同一个慢传输在正式收集路径按指定预算完成；在剩余时间更短的作者调试/分析恢复路径按授权预算结束，错误保留层次与原因。覆盖实际服务调用点，不能只测适配器方法接受了新增参数。

## R3 — P2：共同观测入口包含资源与进程行为，不能直接视为纯日志能力

计划位置：P4 第2、3项及验收（159—167行）。

现有 `local_process_observation.py` 的 launcher 不仅记录日志：

- 27、153—156行设置512MiB地址空间限制；
- 222—227行覆盖多个计算线程环境变量为1，并关闭标准输入；
- 239—257行处理并终止残留进程组。

将该入口推广给所有允许原生命令的角色，即使仍为可选，也需要明确这些行为是否适用于新调用者。否则角色一旦按新说明使用 launcher，原本可运行的命令可能因额外资源限制失败。计划中的“无权限扩大”并没有涵盖这种行为变化；测试的512MiB预算也不能自动解释为所有角色的新运行限制。

最小修订要求：

1. 写明共同入口复用的是观测能力还是完整执行策略。内存、线程、输入和子进程处置必须沿用该角色既有约束，不能借观测推广默默统一修改。
2. 保留现有分析入口的兼容行为；新增角色的行为应明确且可测试，不为本轮引入新的通用资源策略系统。
3. 延续计划已有的部分覆盖说明：可发现工具不代表所有原生命令已经被观测，不调用 launcher 不能阻断合法提交。

验收补充：检查作者、审查、分析三个角色的实际生成入口与执行参数，确认观测接入没有引入未声明的资源限制或命令语义变化；保持现有分析行为兼容。
