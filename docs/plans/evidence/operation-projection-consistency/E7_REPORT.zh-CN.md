诊断和源码核查确认以下问题：

1. 一次输出拒绝明确要求计算中的案例映射与报告中的正式来源引用及依据一致。`result_analysis.py` 的 `_mapping_fact` 把来源身份、案例、输出名连同 `rationale` 原文和有序证据列表一起序列化比较，`analysis_context` 要求计算请求与报告再次填写的映射完全相等。这会把说明改写或引用排序差异也纳入硬拒绝条件。未读取被拒草稿，因此不能断言本次具体差异就是措辞或排序，也不能把全部拒绝归于同一原因。
2. 同一提交校验器再次调用 `evaluate_tcad_request` 重放计算。最后一条拒绝明确为 `calculation replay budget exhausted; remove this calculation and submit limited analysis`。校验自身耗尽预算后要求 Agent 删除计算记录，已经干扰结果交付。
3. 还有一条拒绝位于 `hypothesis_assessments[0]`，多条只给出通用字段关系错误；具体触发条件未从受控摘要定位。当前源码仍有科学判断与分层状态的强制关系，不能把这些关系全部当作纯格式校验。
4. 此次没有证据表明输出阶段重新执行了输入准入。读取冻结证据核对输出身份和重新评估输入资格是不同动作；不把前述过度校验误报成已修过的输入重准入问题。

问题也存在于既往计划：R4 明确保留了映射理由比较、Worker 重新提交 basis，以及 computed 记录的数值重放。R1 修复了合同传递和部分诊断，却没有重新判断这些义务应由谁承担。“唯一声明、一次编译”只能保证要求传播一致，不能证明要求本身合理。

下一次修订应落实既有职责分工：控制层及工具自动记录已经确定的来源身份、执行关系和计算记录；Agent 负责科学选择、尚未确定的科学对应关系、解释和结论，并引用受控记录。不得要求 Agent 再抄写控制层已知事实来通过第二遍比对。提交阶段保留必要结构、引用存在性及不可变记录完整性检查；重复计算和说明文字相等不应成为正常提交的义务。真实来源错配仍需保护；科学合理性与证据充分性由分析和独立审查处理。以上是针对失败的修订方向，尚未实施。

本轮仅运行一个受控分析 Agent，没有启动求解器、构建或测试进程。E6 要求隔离夹具中的真实新 Agent 完成已知数值及同 Run 纠错；现有命令行派发路径的最低内存配置为 1024 MiB，高于本轮 512 MiB 约束，而原生 Worker 入口绑定生产服务。本轮未建立隔离派发条件，故 E6 保留未验证，不能以单元测试或 E7 替代。此次 E7 也没有可接受的数值结果或跨轮科研闭环证明。
