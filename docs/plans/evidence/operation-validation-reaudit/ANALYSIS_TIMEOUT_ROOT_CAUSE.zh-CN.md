2026-09-12。范围：`fig4_morphology_analysis_1`、`fig4_morphology_analysis_3`，
并以成功封存中央结果的 `fig4_morphology_analysis_2` 为对照。

本报告补充[安装后报告](RESPONSIBILITY_PLACEMENT_POSTINSTALL.zh-CN.md)，不追改其当时的证据边界。
原报告只检查控制层摘要，因此无法拆分时间；本次进一步检查该分析 Agent 的本地会话日志，
仅提取原生命令、返回码、异常及时间戳，不把聊天、内部推理或失败草稿作为科学结果。

## 1. 结论

两次超时均有具体执行原因，不能再笼统归为“没有日志，原因未知”。

- 第一次：准备/编写完整脚本耗去约八分钟，随后两处 Python 错误造成修正与重跑；最后一遍计算
  正常退出时已经超过 Run 截止时间，没有时间整理和提交。
- 第三次：数值计算完成到绘图入口后，因缺少 matplotlib 退出；数值结果原本在绘图之后才写文件，
  因此这次失败未执行数值文件写出。改为 Pillow 后再次从头计算，但余量小于上一遍实测耗时。
- 原生 Python 异常存在于会话工具记录，没有进入 Worker MCP 的工具错误摘要；“没有记录到 MCP
  工具错误”不等于“计算没有报错”。

没有查到这几次进程以 MemoryError、OOM kill 或内存上限失败退出的证据，也没有输出校验拒绝导致
这两次超时的证据。仍未取得历史各拟合函数的 CPU 剖析；该限制不妨碍定位上述直接失败链。

原始 main 的执行顺序为：

```text
循环计算两材料的剩余拟合并在内存汇总
读取已绑定轨迹
plot_results(...)          # import matplotlib 在这里失败
写 resource_evidence
写 completion_results.json
写两个 CSV
```

重试仍调用整个 main，没有“从已存数值结果只画图”的分支，也没有逐拟合持久化检查点。
因此，缺绘图库这个局部问题导致整批数值计算重做。根因不只是环境缺一个包，还包括输出保存顺序、
恢复粒度和未用已知耗时约束重试范围。简单安装 matplotlib 只能消除本次触发点。

## 4. 对照与恢复报告纠正

中央阶段 Run 的实际脚本在 13:34:33.542 启动，13:35:31.552 已返回 0，观察区间约 58 秒；
整个 Run 从创建至封存约 462 秒。不能把全部墙钟时间视为数值计算时间，也不能断言基础拟合本身
必然需要 15 分钟。

续接 Run（analysis_2）打印 assignment 时，其命令只选择了 instruction、inputs、
prior_source_bindings、revision 和 output，**没有打印 recovery_draft**；随后只列举 output 与 scratch。
这些记录不足以支持该 Run 封存报告中“assignment.recovery_draft 为空”的说法。
第三个 Run 的打印确实含 null，但它没有使用 resume_from/draft_from，该值正常。
本次将“续接入口未交付”的归因保持为未证实；工作区快照范围问题与此分开处理。
