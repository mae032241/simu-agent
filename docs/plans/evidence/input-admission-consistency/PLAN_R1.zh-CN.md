## 2. 唯一权威及保证边界

OperationSpec 是操作输入集合、基数、类型与用途的唯一权威；生产者现有 ReviewSpec/review_edge 是审查者、被审输出和允许结论的唯一权威。消费者接收审查的能力由二者共同推导，不再复制审查者或通过结论清单。

优先复用现有声明：本轮不新增 review_for、依赖图、持久化审查索引或状态机。编译器从生产者审查边、审查者输出与消费者输入的类型兼容性推导候选接收端口。运行时再按实际对象的生产者合同验证精确绑定；类型兼容只意味着可以接收，不代表已经通过审查。

三个层次分别保证：

1. 编译：已注册合同之间存在满足准入要求的接收方式。
2. 准入：本次实际绑定的审查确实来自匹配的完成态独立 Run，对应精确被审对象且结论符合规则。
3. 实现：只处理框架校验后的业务输入，不再定义另一份 Operation 输入准入名单。文件完整性、物理实现、哈希及输出内容校验继续保留。

不能声称静态检查证明任意 Python 实现、任意未来插件或科学判断正确。实现遵守合同由实际入口集成测试验证；未注册的生产者、不可兼容历史合同仍由运行时明确拒绝。

## 4. P1：修复打包合同与重复实现名单

改动 `operation_transforms.py`：

- 为打包声明 `experiment_review`，使用通用科学现有 scientific-review schema/codec，基数 0..1、用途 prior_signal。可选表示没有生产者审查要求的导入对象仍按旧规则处理；真实生成计划的证明是否必需由实际 review_edge 决定，不由可选端口放行。
- project 的证明仍为现有 review；计划证明为 experiment_review。不得拿 deck review 代替计划 review，也不得自动继承父对象资格。
- 保留 package_parentage 对 project/review/capability/plan 的精确关联检查。
- 包装器显式提取业务函数需要的四项操作数；审查证明由框架消费并保留为此次调用的不可变输入父记录。包装器不对完整输入集合另设白名单。

改动 `transform_adapter.py`：将 `package_reviewed_project` 的 Mapping 全量准入接口改为四个显式关键字业务参数，移除重复的输入集合校验。同步仅修改其实际调用者和相关测试。解析与内容校验保留。业务参数清单不是 Operation 端口清单，控制证明无需为了凑业务参数进入算法。

验收：新端口可在目录中看到；经框架传入该证明不被包装器/实现拒绝；旧四个业务输入内容和打包结果语义不变。缺失、错误或未通过的计划审查均不能让真实生成计划进入打包实现。

## 5. P2：共享审查接收规则与编译检查

主要文件：`operations/catalog.py`、`operations/invoke.py` 或一个有编译与准入两个实际调用者的小型纯函数模块，以及 `mcp_root_operation_routes.py`。仅在需要公开派生诊断字段时修改 spec 的目录投影；不改变科学对象 Schema。

实现顺序：

1. 提取现有准入分支的结构性规则，编译与运行时共用；不能另写一套“近似”的编译规则。包括审查本身的豁免、现有直接修订规则与 evidence_inventory 的背景语义。
2. 对目录中类型兼容、消费者可能接收的已注册生产者输出，检查其 review_edge。普通消费必须至少存在能接收对应 reviewer 输出的输入端口。比较 schema、codec、资源兼容性及容量，复用已有兼容检查口径；不只比较端口名或 schema 字符串。
3. 多生产者同 Schema 时按每条已知生产者审查边检查接收能力；运行时只要求实际绑定来源的证明，不要求调用者携带所有潜在来源的审查。
4. 可选被审输入未绑定时不要求证明；集合容量要足以表达实际允许的被审对象数量，允许现有合法共享审查，不能简单要求“一端口对应一端口”。静态无法确定实际分组时明确交给运行时，禁止猜测判通过。
5. 背景查阅、blocked 对象的审查、非通过审查驱动的直接修订继续可表达。不能把 prior_signal 一律当作免审背景，也不能借用途变更绕过执行前资格。
6. 缺少接收能力时编译拒绝，建议错误码 `input_review_receiver_missing`，定位 consumer operation、subject port、producer、reviewer；不添加自动补输入、自动重审或静默降级。
7. 运行时仍调用现有精确 reviewer 验证，保留完成态、合同兼容、独立性、精确 subject 与 verdict 检查。候选端口识别使用共享规则；失败返回明确缺少哪种证明，而非仅泛称 missing。

所有声明的端口仍由 preflight_operation 校验未知输入、缺失输入、基数和类型。不得依靠调用者自觉或插件内部校验替代此边界。

- 正例：真实生成计划及精确通过审查，通过作者、源码审查和打包的 Root 入口。使用小型固定科学载荷和受控提交测试设施，不启动 LLM 或 Sentaurus；不可直接注册计划来规避生产者合同。
- 参数化负例：计划审查遗漏、另一计划的 pass、同一计划的非 pass、错误 reviewer，均在业务实现调用前拒绝。记录实现调用计数以证明边界。

资源约束：串行、BLAS/OMP 单线程、每批超时 120 秒、测试进程地址空间上限 3 GiB，记录峰值 RSS。不得运行全量、压力或并行求解器测试。失败先定位，不扩跑套件。

## 7. P4：兼容、部署和真实验收

变更将影响打包操作合同及相关组件摘要。实施前用现有 producer compatibility 机制评估影响：只变更必要版本/组件身份，不全局提升 ABI 来使所有历史资格失效，也不无条件兼容所有旧摘要。

旧 Run、计划、源码与审查内容保持不可变。验证当前 plan_3、experiment_review_6、author_4、deck_review_5 在新部署中仍符合既有资格规则；若发生摘要退役，必须说明具体合同变化与原因，不能为工程升级重做科学内容来绕开。

部署后使用新语义名称提交打包请求，显式绑定原计划审查。前置条件是新目录编译通过且精确预检通过；否则不创建执行请求。

打包成功后创建六案例执行审批请求，给出控制返回的 URL；只有 UI 封存批准才 execution_start。同步执行并保留真实日志及原始输出；即使失败，也进入目录允许的有限结果分析或诊断，不把缺少部分输出一概变成无法分析。

工程合同修复完成标准：真实原记录可打包，错配证明仍被拒绝，执行请求可按既有审批规则创建。端到端研究验收另记录实际执行/分析结果，不把合同修复或初始化成功当作研究目标完成。

## 8. 实施顺序和停止条件

严格按 P0 → P1 → P2 → P3 → P4。P1/P2 作为一个候选共同验收，不将放宽检查的中间版本部署。当前只制定计划，不修改运行源码或部署。

若必须新增全局来源限制、统一依赖图、状态机、批量调整科学合同或自动资格迁移才能落地，停止并修订方案，不能借“一致性”扩张范围。每项修改必须对应本次不可满足的合同，或能阻止同类明确矛盾的编译/运行时检查。

交付证据包括：本次失败快照、同类入口短表、变更文件及理由、定向测试与安装检查日志、兼容影响、部署后精确预检结果。不得以测试数或编译通过替代真实绑定链的验收。
