# 全局整改根因再分析

状态：用户要求对症分析后的设计修订依据，尚未独立审查。R2的历史计划审查PASS保留，但不能据此直接实施下文指出需重定型的B/C/D设计。Fig4继续暂停，不改源码。

## 判断

不能把所有现象归为校验过严或Agent不遵守提示。现有Operation已统一注册和编译，但统一声明不等于所有消费者对同一对象、用途和生命周期采用相同语义。主要问题发生在产物跨角色消费、草稿开发与最终封存、完整记录与模型可见投影三处。

### 根因一：可追溯产物不等于可交付任务

ToolEvidenceManifest有bindings/records/attempts，保存来源与工具历史；analysis_artifacts.publish_analysis_file的derived_from给出来源关系。但来源、实际读取、复算必要依赖不同。Root目前必须理解分析正文和脚本历史才能组装下游任务，机械闭合依赖模型推断。由此出现算法漏绑、原表漏绑、局部别名错用、大量前置阅读。

通用修复应以“消费用途”为边界：Agent选择要审查/复算/实现的科学对象，控制层用该对象已登记、用途明确的交付关系生成完整的任务视图并冻结。来源身份在产生时的上下文中解释，当前别名只是投影。领域生产者登记其确知的使用关系；未知科学相关性仍由Agent判断，不能从所有parents推导。

审查可能只需核心原始依据，复算需要算法和原表，实现需要方程、参数与能力；不应为三者都自动展开同一大包。不是新增统一成果大JSON，而是现有Artifact/manifest/Operation间一个用途明确、可访问但按需展开的消费约定。图结构、端口与具体字段只是实现手段，不能先定端口扩容再反推科学职责。

### 根因二：不同用途的检查共用不适合的完成条件

TCAD工作区初始handoff只含附加说明，开发preflight却调用最终RoleHandoff完整校验。没有科学结论的开发候选因此被要求填结论字段；生成模板和消费者失配不是靠加两个默认字符串根治。

修复原则：根据动作声明它实际需要什么。开发候选检查源码、声明和可运行性；成果封存检查科学交付；执行检查精确源码/审查/授权。共享相同底层来源和结构定义，不共用所有阶段的完成要求。控制层生成的字段不再让Agent填写或承担其缺失错误，科学内容不能伪造默认值。

### 根因三：可变工作记录与不可变科学证据混用

operation_workspace._write拒绝不同字节覆盖是保存不可变输入时的正确规则；materialization失败分支却将它用于运行中变化的报告，同名旧报告掩盖新诊断。插件又重复记录已存在拒绝，造成错误统计失真。

应统一既有对象的写入语义：输入/封存产物不可变；开发草稿可改；尝试诊断追加；当前摘要可重建。一条错误由最先掌握事实的边界登记一次，包装层只引用或补充上下文，不再登记同一事件。不必新建状态机或通用文件系统，只收敛现有读写/诊断接口及调用者，完整扫描同类生产路径。

### 根因四：能力存在性和当前实现可行性没有准确传给设计者

编译目录知道哪些动作可调度，域能力知道求解器版本；设计任务没有完整消费这两个层次，Root又倡导尚无入口的路线。初始化可成功不等于accepted-step输出可用，两者也不能靠接口列名证明。

通用修复是从同一注册定义投影当前允许动作，并明确“已声明能力/需有界验证的能力/当前不存在”。设计者据此选方案，作者验证具体实现，审查者区分科学缺口与尚待实现。不是新增能力审批或让程序自动决定用哪个模型，更不是为Fig4补专用执行器。

### 根因五：存储对象直接成为阅读单位，且无效交接反复放大它

Root status含大段重复信号，Worker批量翻页汇总，compact intent再物化完整计划后多次重读；都是没有按决策目的选择信息。已有局部摘要/reader不是完全缺失，问题是组合路径仍允许全量读取与重复投影。另一方面，很多token来自本可避免的整轮返工；压缩返回字数无法消除返工。

通用修复应先减少交接失败，再为每个动作提供决策视图、精确原件入口和可选细节；完整记录留存，字段只在有消费需要时展开。框架注册工具可限制返回预算；宿主shell/JS由模型控制，不能虚称全局硬限制。原生提示与观测是边界补充，不能替代控制接口的正确投影。

## R2应如何重排

1. A保留但改成开发/封存用途与派生报告生命周期的一致性修复；不是仅补handoff字段、删一个计数或覆盖一个文件。
2. B先定义可交付任务的用途与关系，证明任一选择的成果在相应用途下可以被下一角色独立消费，再确定manifest/端口投影。R2的2跳、8依赖、4→12只是未经测量的候选容量，不应成为架构原则或一揽子扩容决定；沿现有编译限额做有据的最小调整。
3. C并入任务准备时的能力视图；不把它降为补一句TCAD提示。区分软件能力待验证与科学参数尚未定义。
4. D基于已闭合交接做按需视图，不靠强制读取登记或隐藏关键限制省token；避免为减少目录查询又强制每轮读完整Schema。
5. E用同一交接契约验证所有Agent类型及相关工具/Transform/恢复路径，领域组件各自声明、核心不按插件名分支。验收机制用至少一个非TCAD简化fixture证明通用性，无需注册新的生产执行器。

## 验收需证明根因已消除

- 新Agent只凭任务视图可定位目标、当前科学对象、相应用途的必要依赖，不需Root读脚本手工找文件。
- 重排输入别名、换Worker、新Run消费不会改换原引用含义；历史关系未知如实标明而不伪造。
- 开发预检不要求尚未产生的科学结论；输出封存不重新做输入准入；审批不因材料可读而继承。
- 连续不同失败保留真实原因且不重复计数；成功后旧失败仍可追溯。
- 明确缺少执行入口时设计者能换现有路线或提出能力缺口；数值/软件失败不成为物理反证。
- Root交接额外阅读、重复Run数和峰值上下文一起下降，科学证据完整性不下降。用量不以cached累计作窗口；必要独立审查保留。

以上属于通用机制修复，但并不意味着所有历史资料都能自动获得正确依赖，或科学设计不会再出错。科学错误仍由独立审查处理；控制层应消除的是机械交接的不确定性，而不是替代研究判断。
