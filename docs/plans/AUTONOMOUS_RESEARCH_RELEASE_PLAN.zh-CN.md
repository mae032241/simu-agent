## 1. 本次发布边界

本计划负责[总路线](SCIENTIFIC_CONTINUATION_AND_SIMPLIFICATION_PLAN.zh-CN.md)中的第二次发布。
它细化并替代总路线 P2/P3 的实施细节，以上下文、诊断、观测与精简能力的实际交付为前提；
实施前核验这些依赖，不预先认定发布 A 已完成。
依赖能力由 [A 版计划](STABILITY_AND_SIMPLIFICATION_RELEASE_PLAN.zh-CN.md)负责，增强体验由
[C 版计划](RESEARCH_DELIVERY_EXPERIENCE_RELEASE_PLAN.zh-CN.md)负责；B 的最小控制与成果界面仍在本版完成。

| 发布 | 交付 | 与本版的关系 |
|---|---|---|
| A 稳定与精简版 | 已知缺陷修复、上下文与诊断统一、基础用量观测、hardened 退役 | 独立安装和回滚节点；本版先确认依赖能力，不把旧缺陷藏进自动循环 |
| B 轻量自主推进版 | 受控 Root、完整任务接续、等待、恢复、用户控制、最小结果与消耗界面 | 本计划的实现和验收范围；默认不自动激活目标 |
| C 交付体验完善版 | 丰富研究视图、变更影响、报告与成本对照体验 | 最小结果读取和必要控制必须在 B 完成，只有增强展示后置 |

三版串行发布，分别保留可安装候选、数据变更说明、验收记录和回滚边界。不要求一次实现总路线。
B0a 能力核验在 A0 后提前串行进行，只依赖当前可运行候选和基本止损，不等待 A2–A5 全部精简。
B0b 在 A 发布后做正式集成；若 A 的某项并非 B 的实际依赖，可明确后置，不能静默降低依赖或扩大范围。

### 1.1 本版必须达成

- 用户明确目标并启动后，后台能够连续完成至少两项完整任务，后项由 Root 根据前项封存结果选择。
- 关闭交互终端后仍能推进；重开界面可读取结果、暂停或接管。宿主实际能力必须先验证。
- 外部条件未变化时程序等待；不周期性调用模型重复询问相同状态。
- 中断、重复唤醒和未知提交能够恢复或明确阻塞，不重复创建外部副作用。
- 普通实验子环节由同一负责人连续完成，按需使用助手，不逐阶段调用 Root 或增加审批。
- 结果、附件、剩余问题、停止原因与用量能在现有界面读取。

### 1.2 明确后置

多实例并行、多运行时、远程团队调度、长期记忆、复杂工作图、全库合并、安装器重写和 OS 强隔离。
本版采用可信本机边界，[SEC-002](../../SECURITY.md)不因框架启动了 Root 而自动关闭。

## 2. 用户交互合同

### 2.1 启动

1. 用户在管理页选择实例；未绑定时返回准确管理入口，不替用户选择默认实例。实例选择只建立当前会话的读取上下文。
2. 用户通过聊天提出目标和范围，并明确启动自动推进；或在已有目标页执行启动操作。
3. Root 复用已有目标和材料，必要时澄清真正缺失的科研信息；不要求填写端口、身份、租约或工作图。
4. 控制层继承该明确选择，绑定后台宿主、目标版本和配置预算，登记唯一推进任务；保留原交互会话的读取关系。
   已有写者时按启动/接管命令原子处理所有权，页面选择不自动接管；重复启动同一活动目标返回已有任务。
5. 返回简短启动回执：目标、当前动作、配置预算摘要、暂停入口。普通启动不再增加第二次确认。

聊天中的研究指令可启动和调整普通工作，但不能替代已有 UI 中要求的人工执行授权。
每项外部动作继续执行其已有配置策略；有资格自主执行的请求不会因自动推进而重新申请审批。

### 2.2 日常交互

| 用户行为/运行事件 | 系统行为 | 是否唤醒 Root |
|---|---|---|
| 查询进展、结果、消耗 | 读取当前投影；在回答中保留时间和缺测信息 | 查询本身不触发后台决策 |
| Worker 普通阶段交付 | 更新阶段与图件展示；负责人继续 | 否 |
| Worker 最终结果或需上层处理的失败 | 汇总新事实，合并同批通知 | 是，且有预算 |
| 求解器仍运行、依赖未恢复 | 程序按配置等待或只读探测 | 无变化时否 |
| 系统配置故障 | 登记故障层、修复责任和恢复条件，停止盲重试 | 首次需要判断时一次，后续合并 |
| 用户补充材料/修改方向 | 保存用户来源、生成目标修订或待处理消息；在安全边界应用 | 是，或者使当前决策过期 |
| 缺少关键用户信息 | 显示具体问题、影响和可继续的范围 | 提问后等待，除非存在已授权独立工作 |
| 需要现有人工审批 | 展示准确审批页，按密封决定继续 | 不反复询问同一审批 |
| 目标结束或资源限制 | 交付成果、限制、停止原因与消耗 | 最多完成必要收尾，不再派新任务 |

若当前聊天客户端无法接收异步消息，结果留在持久通知列表和 UI，下一次连接补读。
不得承诺所有客户端关闭后都能收到推送；通知送达状态与科研任务完成状态分开。

### 2.3 暂停、停止、取消、接管

- **暂停推进：**立即持久化暂停意图，禁止后续 Root 调度写入；已经接受的动作回读归档。
  已启动 Worker/外部作业默认继续并保存结果，不把暂停解释成取消。
- **恢复：**读取实际 Run、预算和等待条件；用户明确恢复撤销暂停，但不自动扩大额度。
- **停止推进：**停止新派发并保存当前成果。仍运行的任务要清楚列出，不能显示成全部停止。
- **取消当前任务/作业：**通过既有取消接口单独执行；只有权威状态确认后才显示已取消。
- **交互接管：**持久交接调度权；旧后台 Root 的迟到调用不能再创建任务。后台可继续只读观察和接收成果。
- **修改目标：**冻结新版本，旧记录保持原版本；明确在途任务如何处理，不能悄悄把旧结果改为新目标已通过。
  可复用材料仍可作为精确输入；含糊且影响在途副作用时才请求用户澄清。

已获准且明确选择实例的会话可查询状态，不因失去调度权而失去读取关系。对自动目标的调度变更必须经过
显式控制命令/接管，不允许交互与后台两个有效调度写者。实例选择与调度权的入口规则见第 3.4 节。

## 3. 最小架构

```text
聊天 / 既有 UI
    │ 启动、查询、补充、暂停、接管
    ▼
推进服务：持久状态 + 单一调度权 + 等待检查 + 用量预算
    │ 有变化且需要科研判断
    ▼
RootHost：一个受控宿主 → 精简研究上下文 → Root
    │ 既有 public Operations
    ▼
RunService → 完整任务 Worker → 可选原生助手
    │ 阶段结果 / 最终封存 / 失败 / 外部作业状态
    └────────── 回读、核对、持久接续、用户展示
```

### 3.1 模块落点与依赖

| 能力 | 首选落点 | 保留与删改原则 |
|---|---|---|
| 推进状态与协调 | 现有 service 层的窄服务 | 不塞进 RunService，不复制 Run/Artifact 生命周期 |
| Root 宿主 | 平台适配边界 | 只实现一个合格宿主；不侵入领域插件 |
| 决策上下文 | 既有运行/科学结果投影 | 复用封存结果与有效引用，合并重复拼装 |
| 唤醒与恢复 | 推进服务 + Run 公开接口 | 不把 lifecycle_events 读取当作可靠消费完成 |
| 用户控制 | 现有 MCP facade、CLI、管理 UI | 读取选择与写者分离；旧选择/attach 入口同样接入，模型不填代次 |
| 归档与维护 | 既有实例归档/维护服务 | 新记录声明表与实例归属；维护阻止唤醒，恢复不复活旧调度权 |
| Token/预算 | 发布 A 的用量与配置 owner | 用真实调用身份归属，父子与失败消耗不重复或遗漏 |
| 持久化 | 现有控制数据库中的必要记录 | 不新增数据库文件；跨库步骤通过持久意图和幂等回读协调 |

RootHost 内部职责为启动/恢复决策、观察实际会话、读取用量、结束或中断会话。
接口名称和协议在宿主实证后确定，不预设 app-server、CLI 或某个命令天然满足后台 Worker 生命周期要求。
实际线程坐标来自宿主；调度身份、实例绑定、所有权代次由控制层处理，不能让模型伪造或手填。

### 3.2 必要持久信息

- 实例、目标确切版本和配置快照/版本；实际预算消耗归属。
- 推进模式：active、waiting、paused、stopped；原因单列。
- 获准会话的实例读取关系，以及独立的调度所有权代次、宿主实际会话绑定、健康状态；二者不共用唯一索引约束。
- 当前决策身份、输入状态版本、已接受调用及创建的 Run 引用。
- 已处理位置、待处理变化、等待条件、检查时间和失败尝试记录。
- 待用户处理事项、通知投递情况和最终结果引用。

这些是控制层内部信息。公开只投影科学目标、进展、阻塞、预算摘要和用户能执行的动作。
科研是否达成、进程是否结束、交付是否完整分别表达；一条 Run completed 不自动结束目标。

### 3.3 一轮推进的持久边界

1. 读取权威状态，合并重复变化，判断是否值得调用模型；没有变化则等待。
2. 持久登记本轮身份与输入版本后启动 Root，记录已开始的宿主调用和预算预留。
3. Root 使用现有合同作出科学选择；控制层自动关联本轮及幂等调用身份，正常工具不增加填写字段。
4. 命令接受前检查调度权及目标版本；先有持久派发意图，再创建/核对实际 Run。
5. 回读实际结果后完成本轮处理记录；只有结果或待办已持久化，才能把变化标为已处理。
6. 进入等待或下一次判断。Root 退出、工具回复成功、通知送达均不能单独作为目标完成依据。

恢复按同一轮和调用身份核对，不能自动换名称重跑。观察至少可重放，副作用依赖既有幂等身份和权威查回；
不宣称全局 exactly-once。若外部接口不支持查回，记录 unknown 并停止该提交路径。

### 3.4 会话读取、调度所有权与旧入口迁移

当前 `scheduler_bindings.py` 在绑定新会话时删除同实例其他会话，并对 `scheduler_sessions(instance_id)` 建唯一索引；
`mcp_root.py` 的实例读取依赖该绑定。只增加推进表会使后台宿主与交互查询互相撤销绑定。
B1 必须在既有绑定 owner 内迁移语义：同实例可有多个获准读取会话，仅有一个有效调度写者。
这不是新的多用户授权体系，也不解决 SEC-002；读取仍受现有实例和调用方权限约束。

| 现有入口/调用 | 迁移后必须遵守的规则 |
|---|---|
| 管理页选择、`bind_session_by_name` | 只改变当前会话读取选择，不删除其他读取会话、不隐式撤销/取得调度权；显式接管调用共享处理 |
| client-state / 重新连接 / `_instance_id` | 返回会话明确选定的实例与适用权限；新会话没有可验证选择时仍由用户选择，不默认继承实例 |
| 后台 Root 启动/恢复 | 由控制层继承用户已选实例并登记真实会话，再核对唯一写者；不伪造 session/thread 元数据 |
| Operation 调用及变更目标 | 所有引起调度写入的入口在提交边界检查实例、目标版本、维护状态和写者代次；只读描述/状态不要求写权 |
| standalone execution 的写操作 | 启动服从同一写者检查；取消/恢复等用户命令按既有资格和确切对象执行，不提供隐式抢权通道 |
| gateway `worker_attach` / 派发恢复 | 与既有 Run 的已接受派发意图核对；不能让失权 Root 通过迟到 attach/start 启动新工作 |
| Worker 阶段交付、最终封存、执行收集 | 沿原 Run 与执行权限继续，不能因父 Root 暂停/失权而一并拒绝；实例维护另按第 3.5 节协调 |

迁移已有绑定时可保留读取关系，不因读取记录自动创建或启动推进目标。所有权和调用身份由可信控制入口关联，
无需 Agent 增加字段；交互修改、自动调度及旧管理页均使用同一所有权处理。
暂停/接管时区分未派发意图与已实际启动 Worker：前者不由旧 Root 继续派发，后者由控制层核对并恢复必要连接，
保留结果提交。原生进程是否已启动不明确时先查回，不依据 attach 回包缺失推定没有执行。

### 3.5 新增记录的归档、维护与恢复

`instance_archive_records.py` 对数据库表有显式允许清单与实例归属映射，未知表会在选择实例记录之前被拒绝。
每项新增持久记录必须同包接入既有归档声明和归属查询，不能关闭未知表检查或另建一个 DB 绕过它。

- **归档范围：**保存目标确切版本、配置身份、科学结果引用、已接受意图、预算消费/待核对预留、等待原因和用户待办。
  会话秘密、活跃租约及可恢复权限不作为可复活执行凭据；通知保留逻辑身份/处理事实，传输会话重新建立。
- **维护范围：**唤醒、取得调度权、恢复宿主、提交推进状态和通知/用量写入都服从既有维护门。
  维护开始后不新派发，核对在途 intent、宿主及 Worker/助手真实写入者，按既有协议等待或有序停止，再取一致快照。
  暂停推进或 Run 终态均不足以证明可以归档；尚不能安全静止时拒绝该次归档并说明原因，不终止正常 Worker 来凑通过。
- **归档恢复：**消耗与确切结果不重置；未决预留先核对，不能当作新额度。恢复的目标保持停用，清除活跃所有权，
  不重绑旧会话、不自动唤醒 Root/Worker/助手、不重发通知或外部提交；用户明确选择并恢复后才核对在途工作。
- **原地服务重启：**按持久意图/权威状态核对并使用新有效代次，可恢复原先 active 且未暂停/维护的目标；
  与归档恢复保持不同策略，不能用“服务自动恢复”绕过导入后的停用状态。
- **兼容边界：**无推进记录的旧实例在新库结构下仍可归档；既有 archive/schema 版本机制显式记录新增语义。
  不支持的旧版本明确拒绝新格式；保留旧归档可读和安全恢复，不能静默丢掉消费事实或降级成自动启动。

完整实例归档与 C 的科学报告导出使用各自既有语义；后者不携带调度权限或替代前者的恢复协议。

## 4. 详细实施包与 Git 交付点

每包串行由一个执行者负责；大节点按需要进行独立审查，不为每个小环节固定增加审查者。
每包提交可复核 Git 节点；是否部署依据该包交付范围，不把源码通过写成正式环境已生效。

### B0：提前能力核验与发布候选集成

**B0a：A0 之后立即核验；不等待 A2–A5。**

- [x] 固定当前 dev 隔离候选、配置和最小试验范围；核验现有认证、工具、实例和资源止损入口。
- [x] 在隔离安装中启动受控 Root，通过实际工具派发 Worker，取得真实平台坐标并回读封存结果。
