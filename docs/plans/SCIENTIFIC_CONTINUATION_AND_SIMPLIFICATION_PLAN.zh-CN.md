## 1. 总路线目标与文档关系

本文件为跨版本总路线，不再作为一次性发布清单。分三次串行交付：A 稳定与精简、B 轻量自主推进、
C 交付体验完善。每版独立提交、安装验证和回滚；不能把全部 P0–P6 积累到一次上线。
详细计划分别由以下文件拥有；本文件只维护跨版本边界与汇总，不再重复维护实施清单：

- [A：稳定与架构精简](STABILITY_AND_SIMPLIFICATION_RELEASE_PLAN.zh-CN.md)：P0/P1、P4 基础精简及 A 发布验收。
- [B：轻量自主推进](AUTONOMOUS_RESEARCH_RELEASE_PLAN.zh-CN.md)：P2/P3、必要控制/成果界面及 B 发布验收。
- [C：研究交付体验](RESEARCH_DELIVERY_EXPERIENCE_RELEASE_PLAN.zh-CN.md)：P5 增强视图、版本影响、报告/成本及 C 发布验收。

原 P6 的验收与发布要求分配给每个版本，不积压到 C；P4 中被 B/C 新能力替代的旧代码由相应实施包删除。
下文规模合计使用三份子计划的新估计，替代早期 P0–P6 粗估，不与子计划再次相加。

用户启动一个已绑定实例中的研究目标后，框架能够串行推进完整研究任务；外部条件未变化时等待；
中断后安全接续；交付可以被用户和后续任务读取的结论、证据、限制以及消耗记录。

本计划沿用当前[科学设计章程](../architecture/SCIENTIFIC_AGENT_DESIGN_CHARTER.zh-CN.md)及架构中的完整任务、
科学所有权、自动机械绑定和按需助手原则，新增目标级接续能力，不另建科研流程或任务权威。
R4 等旧计划从 `5a90f3f` 的 Git 历史按原路径读取，不恢复为当前依赖；历史验收仅适用于当时的精确候选。

当前架构见 [ARCHITECTURE](../ARCHITECTURE.zh-CN.md)，已知信任限制见 [SECURITY](../../SECURITY.md)。
实施时同步修正受影响的当前规范及中英文对应章节；历史审查和原始证据不改写。本计划及计划首页
是本轮规划入口，不把实施流水账继续追加到多个旧计划，也不把规划文档加入 Agent 正常启动材料。

借鉴 LoopX 的有界决策材料、持久接续、明确等待、失败恢复、成果回读和用量记录；不引入其完整
Goal/Todo/gate/quota 系统，不引入 Python/TypeScript 双语言控制层。

### 1.1 完成标准

1. 一个目标至少经历两项完整任务；后项由 Root 根据前项实际结果选择，不预先写死科研路径。
2. Worker 保持完整任务所有权，可按需使用原生助手；普通阶段继续执行，阶段结果自动进入 UI。
3. 无变化等待不反复调用模型；明确区分系统故障、科学负结果、证据不足与目标达成。
4. 重启、重复通知、派发回包丢失不会导致重复任务；未知外部提交只核对原提交。
5. 用户能够暂停、恢复、停止和接管；同一实例没有两个同时有效的 Root 调度者。
6. 必要科学字段及其规则完整可见；机械字段由控制层产生，内部身份与绑定不暴露给科学 Agent。
7. 成果、附件、下游消费和 UI 对应同一确切对象；Token 与失败消耗可追溯，缺测不记作零。

## 2. 实施约束

- 全程串行；每个实施包可以交给一个独立执行者，但不并发启动实现、测试、安装或真实模型任务。
- 一个负责人完成设计、实现、局部调试、执行和分析；不按子环节固定派发 Agent。
- Root 决定科研方向，控制层决定绑定、预算、是否需要唤醒以及机械恢复；助手建议不自动成为正式独立审查。
- 普通环节不新增审批。重大节点仅执行已有明确资格/授权要求；独立审查按需要发起。
- 现有配置允许的自主执行范围继续有效，不因后台循环再申请一次审批。重试和恢复不扩张授权或预算。
- 保留 Operation 编译器、catalog ABI、组件身份、版本化 Schema、不可变 Artifact、来源及审查精确绑定。
- 查询保持只读；健康检查不创建外部作业，状态读取不隐含提交、收集或取消。
- 运行、重试、等待、上下文和资源阈值集中到现有配置体系，Agent 不逐轮填写。
- 失败不算成果，但失败的模型调用、墙钟、外部任务和尝试次数仍计入相应实际消耗。
- 控制面与 Worker 同 UID 的 SEC-002 保持未关闭。调度唯一性不等于身份安全或 OS 强隔离。
- 自主推进版只支持一种受控 Root 宿主；不以全面兼容多个运行时阻塞交付。

## 3. 目标架构与最小持久信息

```text
用户已选实例 + 已绑定研究目标
                │
                ▼
推进器：预算 / 调度所有权 / 变化检查 / 等待与恢复
                │ 有需要判断的新事实
                ▼
精简研究视图 → 受控 Root → 现有 public Operation 调用
                                   │
                                   ▼
                         Run → 任务负责人 → 可选助手
                                   │
                      阶段交付 / 最终封存 / 明确失败
                                   │
                    持久推进记录 + UI + 消耗观测
                                   └── 再判断是否唤醒
```

### 3.1 各层所有权

| 层 | 负责 | 不承担 |
|---|---|---|
| Root | 根据目标、证据和限制选择完整任务，解释调整方向或结束理由 | 文件身份、租约、游标、重试账本 |
| Worker | 完成任务与阶段结论，判断方法和结果，整合助手 | 维护全局任务图、重复填写机械元数据 |
| 推进器 | 持久接续、单一调度者、唤醒、等待、预算和恢复 | 自动推导科学结论或强制改变机制 |
| 既有控制服务 | Run/Artifact/Approval/Execution 的唯一状态权威 | 为推进器复制一份业务状态 |
| 插件 | 领域工具、执行能力、健康探针和领域计算 | 通用调度、Root 身份和全局预算 |
| UI | 当前状态、结论、证据、消耗及明确的控制操作 | 存储第二份研究进度真相 |

### 3.2 接续与故障细节归属

推进状态、所有权、预算、等待、恢复和用户接管的详细规则统一见
[B 版第 2–3 节](AUTONOMOUS_RESEARCH_RELEASE_PLAN.zh-CN.md)。A 提供既有任务的权威读写及安全诊断；
B 持久保存推进意图；C 只读取并展示。不能在三个版本各建立一套恢复机制。
B 同时负责读取会话与唯一调度权分离，以及新增记录的归档/恢复和维护门接入；详见 B 版第 3.4–3.5 节。

现有 `lifecycle_events` 的观察位置不是已处理确认。实现采用可重放观察、幂等派发和权威查回；
未知外部提交不能盲目重发，也不宣称全局 exactly-once。

完成后记录精确提交、新增/替换/删除项及未验证边界，原始日志和大文件不入仓库。

### 4.2 发布顺序与阻塞处理

**发布顺序保持 A → B → C，能力核验提前：**

1. A0 固定当前候选、已完成修复及实际消费者。
2. 串行执行 B0a：用当前隔离候选验证真实宿主派发、身份、生命周期及资源止损；不等待 A2–A5 全部完成。
3. 完成 A 必要修复、共享能力及退役，独立发布；A5 非 B 必需的广泛收敛显式后置。
4. B0b 将已验证宿主集成到 A 发布候选，再执行 B1–B6；既有实证只重验受影响边界。
5. C0–C6 增量实现及发布。

若 B0a 被现有缺陷挡住，只先做让试验可进行的最小修复；宿主不满足要求时修订 B 的路径，A 仍可独立推进。
能力核验不提前发布 B，也不能声明完整自主推进已完成。所有执行者、构建、测试和真实链路保持串行。
每版可独立安装/回滚。A 核心故障与共享接口未合格时，不能用 B 的循环重试掩盖；B 的最小控制/成果读取不延期到 C。

某项如可安全后置，必须在所属计划写明消费者、影响与接收版本，并同步依赖；不静默删去验收。
部署不自动激活目标。回滚先处理调度权和在途操作，不能倒退数据库抹去已经发生的外部提交。

### 4.3 分支与提交约定

本轮按用户明确要求在 `dev` 工作树实现和验证，不切换或直接修改 `123/main`。
通用规则见 [CONTRIBUTING](../../CONTRIBUTING.md)；其中 main-first 修复顺序在本轮以用户指定的 dev 开发顺序为例外，
其余分支职责不变。影响 main 既有功能的修复须与新功能分开提交，标明适用范围和最小回归，供后续 main 维护流程单独回流；
仅涉及 dev 新能力的提交留在 dev。不得把 A/B/C 特性整包带入 main，本计划修订不执行提交、合并或推送。

## 5. 验收矩阵与运行限制

| 维度 | 最小正例 | 必须覆盖的负例/恢复 | 通过条件 |
|---|---|---|---|
| 科研判断 | 根据结果选择下一项任务 | 数据不足、负结果、目标变化 | 不编造成功；依据和限制可回读 |
| 上下文 | 单一启动入口、完整科学合同 | 隐藏端口、长材料、分页、合同变更 | 机械字段不要求填写，必要语义不丢失 |
| 自主推进 | 两项完整任务串行接续 | 重复唤醒、无变化、停滞 | 无重复派发，无无变化模型空转 |
| 宿主 | 真实 Root 与 Worker | 会话丢失、宿主异常退出 | 真实身份绑定与可解释恢复，不伪造线程 |
| 外部效果 | 一次提交与正常收集 | 接受后丢包、未知状态 | 先查原提交；不重复创建外部任务 |
| 预算 | 原目标下累计消耗 | 重试、换线程、助手、缺测 | 不刷新额度；未知不当作零 |
| 人工控制 | 暂停、恢复、接管 | 旧 Root 迟到调用、外部任务仍运行 | 无双重调度；暂停与取消语义准确 |
| 多会话读取 | 后台推进时交互查询/重连 | 管理页重新选择、client-state、旧 attach/start | 读取不撤销写者，过期写者不能派发，已接受任务可交付 |
| 归档与维护 | 旧实例及带推进记录实例归档恢复 | 新表、唤醒竞争、旧所有权、在途写入者 | 归档可用；维护不被绕过；恢复保留消耗且推进停用 |
| 成果交付 | 附件发布及下游读取 | 未登记文件、同名异物、通知丢失 | 精确对象贯穿 UI 和后续消费 |
| 精简 | 单一路径运行 | 旧 hardened 配置、历史归档 | 明确拒绝旧执行入口，保留历史证据 |

所有测试通过 `scripts/run_tests.py` 或等效受控验收入口串行执行，先定向源码，再进程边界、隔离安装、
真实宿主与真实外部执行。安装构建共享产物，不在多个测试中重复构建。只重跑受影响的测试和必要最终集成。

资源控制复用现有配置；总观测包含 Root、Worker、助手及相关子进程，避免各进程分别限额造成总占用失控。
现有地址空间限制与进程树采样不能宣称 cgroup 聚合硬隔离或绝不 OOM；扩大额度不得静默进行。
本计划不自动沿用某次验收临时放宽的内存数值作为产品默认。

实际指标包括：任务结果有效性、完整交付率、重复副作用、人工介入次数、阻塞定位/恢复耗时、Root 请求数、
父子输入/缓存/输出 Token、无变化唤醒、工具回包大小。字节数只用于体积观察，不冒充 Token。
改善目标在基线测量后、候选对照前确定；没有收益时如实标记，不以测试通过数代替产品收益。

## 6. 规模预算与工作组织

以下按细化后的三个版本重新估计，**替代**早期总路线生产 2,950–5,350、测试 1,200–2,100 行的粗估。
细化明确了每版独立验收、恢复边界及 C 的版本/导出体验，范围和测试已展开；不是在旧估计上另加三版。
新增量含现有文件新增代码，不含依赖、生成文件和原始数据；删除量单独核实。

| 发布 | 生产新增估计 | 测试新增估计 | 删除方向 |
|---|---:|---:|---|
| A 稳定与精简 | 850–1,750 | 750–1,350 | hardened、重复合同投影、错误/观测、适配及身份函数 |
| B 轻量自主推进 | 1,800–3,300 | 1,050–1,850 | 临时启动/续跑脚本、重复等待/恢复处理 |
| C 交付体验 | 850–1,550 | 650–1,100 | 重复状态卡片、附件查找、报告和指标计算 |
| **合计** | **3,500–6,600** | **2,450–4,300** | 非净增长承诺 |

以上数值保留为审查前的粗预算，尚未针对新增的会话迁移及归档范围重新估算，不能视为独立审查确认的上限。
A0、提前的 B0a、C0 分别确认现状、宿主和数据能力后修订；B1 设计时重新核算绑定/归档成本，已完成项不重复计入。
hardened 三个专属文件此前约 907 行只是删除候选基数；共享协议、历史读取、科学算法和有效保护不能按行数目标删除。
新增显著超出估计时先检查重复建模及范围增长，不用压缩代码或删必要验证来凑数。

每包由一个执行者串行负责；按完整可复核结果提交，不按字段拆成碎片。
跨宿主、持久化、外部副作用、历史身份和发布等大节点按需要独立审查，普通小修复不机械增加审查阶段。

## 7. 本轮后置项与风险

- 全面合并数据库、全量安装器 Python 改写、为达到固定工具数而合并接口：另行收益审计。
- 领域经验库、语义漂移模型、复杂科研关系图、多宿主和多实例并行：待基本推进收益证明后考虑。
- 普遍强制 holdout、每轮强制独立评估、精修超限强制换机制、每 N 轮强制换 Root：不采纳为通用规则。
