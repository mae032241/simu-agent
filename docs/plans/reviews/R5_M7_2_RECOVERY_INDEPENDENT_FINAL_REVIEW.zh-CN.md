# R5-M7.2 失败恢复独立终审

日期：2026-09-02  
审查范围：当前恢复实现、恢复实跑报告与持久根
`deliverables/m7-live-run-recovery-20260902-01/`  
审查方式：只读代码追踪、持久数据库与文件复算、聚焦回归；未修改运行状态，未启动 Codex  
结论：**FAIL；阻断项 2。M7.2 第 5 项不能关闭，M7.2 整体也不能关闭。**

## 1. 结论摘要

本轮已经真实证明了大部分恢复控制链：故障进程通过 stdio Worker MCP 打开任务并调用已注册领域
工具，留下未提交草稿后以非零码退出；Root 用状态与最后活动时间比较交换记录失败；错误输入恢复在
预检阶段零 Run 拒绝；正确恢复建立了一个身份不同、但 Operation 版本、摘要、指令和完整输入均相同
的新 Run；一个 4 GiB 受限的独立 Codex 重新调用领域工具并完成受控提交；重启后的输出 CAS、父链和
终态可复算，且不存在活动 Run。

但是，这些事实目前只能证明“失败后按相同不可变请求重新执行成功”，不能证明 Agent 实际可用失败
草稿继续工作；同时，恢复链次数没有任何控制面硬上限。前者使 checkpoint 草稿的实际可用性没有被
验收，后者直接违背 `RES-002` 对恢复有界的要求。因此不能把机器结果升级为 M7.2 第 5 项通过。

## 2. 阻断项

### B1：实际 Codex 没有证明能够读取或利用恢复草稿

持久事实确认恢复草稿被正确复制到新工作区、标记为
`scientific_evidence=false`，并保持只读；但这只证明控制面物化正确，不证明模型可使用它。

本次恢复 Codex 的精确角色关闭了 shell、统一执行和图像查看能力，Worker MCP 只提供生命周期工具与
领域 CSV 分析工具。实跑时 Codex 尝试列出 MCP 资源，但服务返回未知 JSON-RPC 方法；无秘密观察记录
明确将 `recovery_draft_content_read_proven` 记为 false。随后虽然领域工具成功一次、最终提交成功，
期间却发生六次 `output_rejected`。持久输出又与草稿内容不同，因此不能从输出相似性反推草稿已读。

这意味着当前正例可以完全由“重新调用领域工具并从头生成结果”解释。它证明重试和最终校验有效，
没有证明恢复草稿这条能力对真实 Agent 可达。六次拒绝本身不是独立阻断，但与资源列表失败共同说明
模型可见的恢复接口尚未闭合。

关闭条件应是：不新增第二运行时或第二状态机，通过该 Operation 明示的最小只读能力，让一个全新
Codex 实际读取任务内恢复草稿，并留下不含内容与路径的可审计读取活动；随后仍必须重新调用声明的
领域工具、校验完整结果并受控提交。不能用模型聊天或输出文本相似度代替读取证据。

### B2：`max_attempts` 未被消费，恢复链没有硬上限

`LimitsSpec` 已声明 `max_attempts`，但生产代码中除 Schema 定义和静态合法性检查外没有消费者。
`RunService` 的恢复校验只检查失败状态、草稿、Operation 摘要和完整输入；调度不会计算恢复链深度，
也不会限制同一失败源或其后代还能建立多少恢复 Run。

当前报告诚实地把主张缩窄为“一次恢复 Run 的时间、单次文件/字节和进程内存有界”。这一缩窄避免了
夸大证据，但不能满足计划第 5 项中的“有界恢复”，也不能满足 `RES-002` 的“时间、字节、来源、
缓存、恢复和并发必须有界”。尤其是本测试 Operation 没有显式提高默认尝试数，却已经成功建立恢复
Run，说明该声明目前不参与授权。

关闭条件应先冻结一个简单语义，并用现有 `resume_from` 边实现，不新增恢复状态机。例如把
`max_attempts` 定义为根 Run 加全部恢复后代的总尝试数，在调度事务内计算并拒绝超限；测试 Operation
若需要一次恢复，应显式声明两次尝试。随后必须增加达到上限后 preflight 与 invoke 同步拒绝、零 Run
写入，以及重启后仍拒绝的负例。

## 4. 两项诚实限制的判定

### 4.1 资源列表失败与六次输出拒绝

- `list_mcp_resources` 失败不是控制面安全缺陷：服务失败关闭，也没有由此扩大工具或读取范围。
- 六次 `output_rejected` 证明格式校验和同一工作区纠错路径实际工作；它们没有把无效候选登记为
  Artifact。
- 但二者不能被当作“只是模型效率较低”而略过，因为本项验收对象包含恢复草稿可用性。没有任何
  可审计读取事实时，本次成功仍是一条从头重跑路径。因此其总体判定是 **阻断 B1**。

### 4.2 未消费 `max_attempts`

- 对当前单个恢复 Run，300 秒 Operation 截止、单文件/字节限制和 4 GiB 启动器限制确实成立。
- 这些边界不能推出恢复链总次数有界；当前也没有自动循环这一事实，不等于调度入口有硬上限。
- 因为设计宪章要求遵守 33 项约束，而 `RES-002` 明确要求恢复有界，所以该限制是 **阻断 B2**，
  不能仅作为后续优化记录。

## 5. 非阻断发现

### N1：失败隔离后仍残留一份 quarantine 候选副本

持久根中除规范 recovery 副本和新 Run 的只读 recovery-draft 外，失败工作区的 quarantine 下还残留
同一只读候选。`discard()` 先把候选改成目录 `0500`、文件 `0400`，随后
`shutil.rmtree(..., ignore_errors=True)` 无法清理该树且吞掉错误。

这没有把草稿升级为 Artifact，也没有让旧 Run 复活，因此不单独否定本次终态和谱系。但它会使失败
恢复重复占用存储，并削弱长期资源核算。应调整删除顺序或显式恢复可删除权限，且不得继续静默吞掉
未完成隔离清理；补一个实际只读候选的清理回归即可。

### N2：本轮验证的是显式失败，不是实际超时

计划写的是“失败或超时”，二者为择一要求，因此真实失败路径已经满足本轮样本选择。超时 CAS 已由
自动化负例覆盖，但没有由这份持久根再做实时超时；不得把本结果扩大为实际长任务超时演练。

## 7. 最终放行边界

当前可以保留并继续依赖的结论是：恢复请求的身份与输入校验已统一，失败草稿不会自动成为科学
Artifact，显式新 Run 可以在受限资源内从相同不可变输入重新执行并产生可验证输出。

当前不能宣称：真实 Agent 已使用 checkpoint 草稿恢复工作，或恢复链次数已经受
`OperationSpec` 约束。因此：

- **M7.2 第 5 项：不通过；**
- **M7.2 整体：不通过；**
- **M7、R5-M：继续不通过。**
