## 1. 这个 agent 是好主意吗？

**思路好，但当前实现没有做好。**

### 1.1 思路成立

长周期 TCAD 研究中，单个对话 Agent 要同时记住论文事实、提出假设、写仿真代码、管理作业、评判自己的结果，这必然失控。本项目把以下几件事分开，动机充分：

- 科学推理（假设、批评）；
- 不可变、带来源的证据；
- 确定性评分与打包；
- 触碰仿真 VM／license 前的人工批准；
- 仿真 deck 的独立审查。

### 1.2 实现已远超其证明的能力

| 指标 | 数值 |
| --- | --- |
| 源码（src + plugins，不含 build 产物） | 约 7.3 万行 Python |
| 测试 | 约 5.3 万行 |
| `docs/plans` | 115 个文件，约 2.6 MB 计划文本（含 evidence 共 141 MB） |
| 自 baseline 以来 | 约 4 周（2026-08-27 → 2026-09-24） |
| Fig.4 科学结果 | 9 个点中仅 1 个有联合改善；"未充分对齐实测"；唯一通过点位于网格边界 |
| 最近一次真实执行失败原因 | TDR 文件实际带 `_fps` 后缀，与声明不符（文件命名问题） |

问题表现：

- **成本过高**：一个文件名不匹配要走完"审查 → 批准 → 执行 → 恢复计划"整圈才暴露。
- **Root 被协议淹没**：`AGENTS.md` 与 8 份指南合计约 6000 词，大部分在教 Root 操作协议（response profile、`view="detail"`、`include_full_output`、资格规则），而不是做科学判断。
- **缺少测量**：Root／Worker token A/B 尚未执行，无法知道这套结构是否划算。

## 2. 原文的批评有帮助吗？

**部分有帮助：诊断正确，具体建议大多合理；问题在于不够狠、不可量化、写法太重。**

### 2.1 合理的部分（基本可以照做）

- **核心判断（第一章）**：科学决策、权限／审查、机械处理三种边界混在一起；前两种值得交接，第三种不应交给 Root。
- **交接标准（第三章）**："接手者是否需要新的独立判断或不同权限"，是可复用的取舍规则。
- **工作包 1**：结果直接给决策视图、机械恢复绑定、派发交给平台，优先级正确。
- **工作包 2**：点名的 `intake.split`、`objective.project`、`execution-plan.project` 都应内收；并指出"只改目录标签为 support 不算完成"。
- **工作包 3**：图证据两个作者环节合并，且保留独立审查。
- **工作包 4-D**：独立审查证明 Transform 退出正常主链。
- **工作包 6**：删废弃路由字段、指南三层化，且坚持"先有接口再删指南"。
- **第七章**：要求证明"交接更少"，而不只是"还能运行"。

### 2.2 有问题的部分

1. **没有目标值**：7.3 节列出了要测什么，但 1.1 节明确不以删除数量衡量，且"不预设百分比收益"，没有给出替代目标（如"每次决策 Root 调用 ≤ N 次"）。工作包 1 做完后仍可能无法判断是否成功。
2. **没有先测基线**：工作包 0 只冻结范围和已有证据；token A/B 仍未执行，本应是第一步。
3. **写法与项目同病**：原文约 33 KB，几乎每条建议后面都跟多条"不能删／不能推断／不继承"，外加整章迁移策略。单看都有道理，叠加后实施成本会重演"计划 → 审查 → 复审 → 验收"的循环。
4. **保守度过高**：第四章处置表几乎全是"保留／内收"，没有追问"真正需要保护的五六条不变量，是否需要 7 万行代码"。
5. **兼容顾虑可能过度**：如"静态搜索不能证明外部客户端未使用公开入口"。本项目是研究原型，外部客户端大概率就是开发者自己，可以用调用日志观察一周后删除。

## 3. 改进建议（按顺序）

1. **先测量（约一天）**：用一个真实决策周期（如"读取 Fig.4 结果并选择下一步"）统计 Root 调用次数、token、须读指南数、Agent 交接次数，作为基线。
2. **明确底线不变量**：
   - Artifact 写入后不可改，并记录来源；
   - 仿真 deck 的作者不能审查自己的 deck；
   - 每次外部仿真执行需人工批准；
   - 数值来自确定性工具，不由 Agent 编写；
   - 结论引用所依据的原件；
   - 失败不算成功。

   其余机制（资格层级、current 判定细则、兼容用输出版本、审查证明 Transform、多种 response profile）都可以考虑删除。
3. **把 Root 的工作变小**：
   - 已完成的 Run 用一次 `run_status` 返回固定决策字段；
   - 选定行动后，服务器自动补齐绑定；
   - 确定性投影／拆分 Transform 在需要它们的行动内部执行；
   - 以上落地后，把 `AGENTS.md`／`scheduler.md` 压缩到约一页。

   目标：每次决策 ≤ 5 次 Root 调用，正常路径不读指南。
4. **合并不需要独立性的 Agent 步骤**：
   - 图证据：选图与 intake 合并为一个作者；
   - TCAD：作者连续完成 deck、开发检查和修正（`_fps` 这类问题应在此发现），之后一次审查、一次批准；
   - 分析：一个任务完成计算 → 作图 → 解释。
5. **停止流程文档增长**：
   - 变更记录每份不超过一页；
   - 工程改动不再走"计划 → 审查 → 复审 → 验收"链；
   - 归档 `docs/plans`；
   - 改动 = 代码 + 测试 + `CHANGELOG` 一行。
6. **有意识地删除无用代码**：
   - 废弃路由字段 `accepts_actions`、`next_action_kind`；
   - 正常路径不调用的 Operation（先记录一周调用日志再删）。

   每一行保留的代码都要能说明它保护哪条不变量。
7. **用科学进展衡量**：把 Fig.4 做完，要么对齐实测，要么在确认数值收敛并加入第二工况后干净地否证。如果系统比"人工 + 脚本"还慢，这本身就是答案。

**以后每项改动的判断标准**：它是否减少了 Root 调用、token 或交接，同时保留了底线不变量？如果没有，就不做。

## 4. R2 相对原文的主要改动

| 方面 | 原文 | R2 |
| --- | --- | --- |
| 起点 | 工作包 0 只圈定范围和已有证据 | 第 0 步先测基线：Root 调用、token、须读指南数、手填字段数、交接数 |
| 目标 | 7.3 节列测量项，但不设目标值 | 硬指标：Root 调用 ≤ 5 次，token ≤ 基线的 40%，正常路径指南 0 份，手填 JSON Pointer 0 个 |
| 保护条款 | 每条建议附多条"不能……" | 集中为六条不变量；说不出保护哪条的机制都是删除候选 |
| 范围 | 六个工作包，分四批 | 只做第一批（原工作包 1、2）；达标后才做第二批；第三、四批并入删除规则 |
| 删除 | 需论证无外部消费者 | 三步：移出模型可见面 → 调用日志观察一周 → 无调用即删 writer，reader 保留 |
| 流程 | 每批有计划、审查和验收记录 | R2 本身就是计划和实施记录；每批一次审查 + 一次复验；历史计划移入 `archive/` |
| 阻断标准 | 九类 | 两条：违反不变量，或未达指标 |

原文中对的内容全部保留：

- 核心诊断与交接标准；
- 第一批的四项具体做法（决策视图、自动恢复绑定、确定性投影内收、派发交给平台）；
- 图证据作者合并，TCAD 作者连续完成方案到开发验证，分析在一个任务内完成；
- 通用分析与 TCAD 分析因权限不同而不合并。
