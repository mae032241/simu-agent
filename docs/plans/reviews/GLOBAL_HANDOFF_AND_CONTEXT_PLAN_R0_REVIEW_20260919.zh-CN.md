## P1-1：B 的核心关系与消费合同仍未定型，不能直接实施

位置：计划 B.1–6、验收 B。

当前 `service/tool_evidence.py:19–65` 的 `ToolSourceBinding` 只有精确 ArtifactRef 与 port_name；manifest 是 bindings、attempts、records、recovery。`read_sources` 是工具实际读取记录，`_evidence_snapshot`（约446行）甚至收集全部绑定输入。二者都不能证明某成果的“下游使用必需依赖”。`_evidence_manifest`（约504行）仅在工具声明 evidence ports 时生成，而且其 parents 同时包括 Run 输入及工具产物。把这些集合直接当作必要依赖会扩大输入、混淆历史背景与科学必要性；仅保留现状则无法保证算法→原表链自动交接。

消费侧不是任意附件通道：`operations/invoke.py:133–206` 要求精确声明端口，并检查同一 Artifact 跨端口重复、基数、别名与总字节；假设反馈端口 `general_science_agent_operations.py:299` 每组最多4项。计划尚未给出分析→算法→原表在这些合同中的精确位置、登记者及冲突规则，也未说明已有生产原件缺少关系时，fixture 是验证历史缺口还是验证新生成关系。两种验收不能混为一项成功。

稳定引用也只覆盖部分路径：`operations/input_validation.py:84` 的 prior_source_bindings 来源于 prior_analysis_sources，`service/run_assignment.py:97` 投影该映射；这不等于任意计划中的旧 current_progress_N 都已有通用跨 Run 引用语义。R0 正确禁止改写旧科学字节，但未冻结新产物引用格式与旧别名的来源作用域。Worker 若只看到新索引，仍可能把旧别名解释成当前同名输入。

最小修订：在 B 增加一张**首版合同表**，而非再建通用依赖引擎：

- 选定一个实际生产链，列根产物、已有来源字段、关系由哪个生产入口登记、何种用途为必需、缺失时的明确行为；只有工具本来知道的执行/重算关系自动登记，科学相关性由作者声明。
- 明确在现有哪一份不可变 manifest/产物元数据上作何最小扩展，关系必须绑定精确产物及来源上下文；历史缺关系不自动补全。旧生产fixture应验证缺口；完整交接fixture使用有来源依据的新关系对象，不修改旧parents、不继承资格。
- 列消费 Operation 的端口、用途、单项/总量限额及最小版本变化；依赖与显式输入重合时复用精确绑定，不重复塞端口；需求用途冲突时有界拒绝。同一来源被多根共享是去重，真正回边才是循环，不能将 visited 命中一概报循环。
- 指定新输出如何表达稳定引用，以及 Worker 如何看到“来源产物的旧别名→本轮别名”映射；控制身份留在服务端。正文不改写，缺失/歧义不猜测。
- 明确同名重试从既有冻结请求恢复，而非先按后来新增关系重新解析再计算指纹。现有 Root `_run_invocation_target`（`mcp_root_operation_routes.py:358–385`）在查同名目标前已计算完整输入指纹；新增解析必须说明插入位置，不能只写“保持幂等”。

首版可以限定为：工具发布时在既有 metadata/manifest 登记工具已知的必需依赖（明确不同于 read_sources/parents）；消费 Operation 显式指定既有 evidence_inventory 用途的目标端口，解析后仍进入现有端口与总预算校验，没有隐藏附加文件。容量不足只作有证据的定向合同调整或返回明确缺口。必须验证该用途符合消费者的实际任务，不通过背景端口补足可信证据资格。完成这张表后再审查 B；其余生产者按共同边界归组扩展，不要求一次覆盖任意 Artifact 的通用关系图，也不新建全局依赖图。

## P1-2：部署策略承诺了当前系统没有的旧合同执行能力

位置：计划 §4“旧Run使用冻结合同，新Run使用新解析”及“每包能单独回滚安装”。

`service/runs.py:1497–1505::_compiled` 按 operation_id 取当前目录项，并要求版本和完整 digest 与 Run 一致，否则抛 `RunContractUnavailable("Run operation contract changed")`。冻结了输入、版本与摘要，不等于保存了可再次加载执行的旧编译实现。当前架构明确区分历史封存结果可读、兼容输入可消费与 Run 续接严格匹配。直接按计划字面实施，会选择隐含引入多版本执行注册，或放松续接身份门；两者都超出最小整改。

最小修订：将策略改为可执行的状态表：

- 完成旧 Run：保持原字节与身份，可历史读取；由现有用途/资格规则决定能否作为新输入。
- 排队/运行/待恢复旧 Run：仅在当前完整编译身份匹配时继续；不匹配明确拒绝原 Run 续接。部署前选择完成既有任务或保持暂停，不隐式迁移。
- 新任务：使用新版本及新冻结依赖；需要迁移时走显式新调用/修订，重新输入准入及版本核验，不自动沿用旧执行审批。
- 回滚：只承诺旧安装可安全读取其支持的历史成果；新版本产物可否解析、哪些执行必须暂停，按包列明。不得将“保留CAS字节”表述成“旧代码一定支持新schema”。

无需增加历史合同解释器。列出受影响 Operation/schema 及一条合同漂移续接负例，即可收敛此阻断。

## 计量和验收：口径可信，但收益尚未证明

现有 `evidence/fig4-handoff-context-20260919/measure.py:34–74` 按 response_id 去重 token_usage_record，单列缓存、输入峰值和工具可见字节，并记录 compacted；观测明确不把字节当token、不把多Agent峰值相加、不把Root历史起点与干净Worker比较。R0 至少两组配对、列波动、不预设节省百分比，是合理的探索性验收，不足以声称统计稳定收益；计划对此已有约束。

建议在实施前将验收登记为可复核的小清单：固定源文件摘要/安装指纹/模型与effort/预算/输入及期望决策；每对样本明确开始和停止事件；用户插话、维护及重试单列；压缩或续接发生时分段报告首值、末值、峰值和请求数。每请求输入差值是窗口净变化，不是新增内容token，不能在压缩后直接累计为“工具新增成本”。工具字节也只表示实际返回的可见载荷，不包含被截断前的原始全量。

功能验收应把依赖漏绑、错误重复、源身份错配、异常定位成功及科学任务结果各自列为 pass/fail/未验收；无数据不放行。先测固定机械响应，再测相同科学要求下的配对原生交接即可，无须引入运行期token阈值控制器。两组样本改善幅度小于波动时只报告未证明收益。
