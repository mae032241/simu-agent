# 准确引用、按需取证 R2 独立计划审查

结论：**REVISE**。方向可行，已避免 invoke 递归补输入、跨端口扩容及历史补关系权威；但“复用现有工具收据”还不是足够具体的实现合同。以下三处必须在编码前明确。计划通过与实现验收分开，本审查未运行测试、科研 MCP、仿真或部署，未恢复 Fig4，仅写本文件。

审查对象：`REFERENCE_ON_DEMAND_REMEDIATION_PLAN_20260919.zh-CN.md`，SHA-256 `358534fb607ff53d08870755dda80354a9c2ab6b47846f79687a6e5dc3890cdf`。静态核对当前 `tool_evidence.py`、`runs.py`、`run_outputs.py`、`input_reader.py`、`operation_tool_context.py`、`mcp_local_worker.py` 和 `operations/tooling.py`；不以旧计划审查代替本版判断。

## 1. 既有对象的读取收据不能直接冒充新工具产物

**位置：计划第4节第4、5条及第7节WP2。** 当前 `service/tool_evidence.py:356` 的 `accept_tool_evidence` 接受原始字节并登记新 Artifact，写本 Run 的 producer 标签、kind/schema和父链。读取已有报告若走这条路径，会产生另一个 Ref、改写生产语义；同内容不等于同身份。若只写 tool_attempt，则 `source_descriptor`（`:201`）只识别冻结 inputs 或 run_tool_evidence，输出校验不能据此取得新来源。两种直连方案均不满足计划承诺。

更隐蔽的问题是：`evidence_output_refs`（`:517`）与 `runs.py:1458` 将所有 run_tool_evidence 视为当前 Run 的产物并绑定发布；`completed_for_output` 也从该路径认定生产关系。若把原 Artifact Ref 直接塞入同一记录集合却不区分记录类型，原对象就可能被当前 Run 当作自己的新产物，破坏生产 manifest 配对。

**最小修订：** 在现有 manifest/收据结构中明确“取得原对象的只读访问记录”和“本 Run 新生产对象”两种语义，沿用同一存储与控制服务，不新增第二套输入表。只读记录保留原精确 Ref/原生产关联、当前根 Ref、可验证的引用边路径、能力合同身份、当前别名和尝试关联；控制层生成。只读记录不重登记原字节、不作为本 Run 生产输出重新发布；source_descriptor、manifest、输出来源校验及恢复均消费同一个判别语义。已有 tool_evidence 输出集合的 kind/schema/数量授权不能自动等同于引用读取授权，需列明编译工具及相关消费者的精确增量。

范围还须明确：每一步只允许已声明提取规则给出的引用边。第5节“生产资料目录”的条目是否可读必须由合同明确，目录出现本身不能自动成为授权；最小首版可将仅目录条目作为导航、未形成授权引用边则继续显式输入。跨报告深入保留原根和每一跳，不仅保存最终 Ref 或当前可伪造的别名。

反例：读取原件后 Ref 和 producer 不变；只读记录不会出现在“当前Run生产成果”中；伪造别名、任意同hash对象、仅目录出现的对象不能绕过引用边授权。

## 2. 部分读取、服务端读取和成功交付尚未区分

**位置：第2节原件/字段/文件入口，第4节实际读取及失败语义。** `OperationToolContext.read_input/read_evidence` 在服务端读取 bytes 后调用 `_source_read`；`mcp_local_worker.py:266` 记录的是整个 Ref/port。`ToolAttempt` 没有字段/页范围；`record_tool_attempt_read` 会保留中断前服务端已读来源；`evidence_sources`（`:325`）与 `runs.py:1236` 又把所有登记来源完整加载给输出校验，不以成功返回某字段为条件。

因此“只看目录”“只取summary字段”“服务端取到文件但返回失败”“已提供文件入口”目前都不能直接解释成“Worker读过完整原证据”。只要登记后自动加入来源全集，计划的“未读目录不能冒充已读证据”仍会落空。框架也无法证明模型实际看过已返回文本，不应建立心理意义的已读账本。

**最小修订：** 明确收据只证明控制服务成功提供的访问范围，分别记录目录导航、字段/页/范围、完整文件可访问，以及成功/失败/中断状态；不宣称已经验证科学内容。选定字段须保留精确原 Ref 与 locator，不因局部返回登记成“全文已读”。输出合法来源由成功的受控提供事实导出；未完成尝试只能作诊断，不自动扩展可引用来源。客户端未收到响应但服务器已封存结果的情况定义为交付未知，可按同一请求取回已封存结果，不能伪称确认阅读或再次登记新科学来源。

服务器内部可读取完整对象作hash/提取，但这与向模型提供的范围分开计量；实现无需跟踪模型记忆，也无需语义判断结论是否正确。既有校验器若需完整原件作机械验证，可以读取，但不能把它自动投影成Worker已取得的全文。

反例：只返回一个字段不能形成全文阅读断言；目录成功不生成原件提供收据；取字节后异常不产生成功来源；重复取回同一结果身份不变。

## 3. 恢复中的授权链与预算继承不能只说沿用既有机制

**位置：第4节预算和恢复。** `adopt_tool_evidence`（`tool_evidence.py:564`）现有分支验证 public_web、derived_from或execution_result，不能验证“根报告→中间报告→原件”的只读授权链；其 origin 还优先取对象的 tool_producer_run，和“当前读取者”不是同一事实。新 Run 即使保留旧收据，也不应因此能读取新根范围之外的对象。

`tool_io_budget`（`:528`）按当前 run_id 汇总固定的字节/时长活动；工具尝试有独立恢复计数，但尚无累计唯一 Ref、选取范围和恢复后的返回预算合同。只保留旧来源却重置成本，会允许通过恢复反复扩大材料集合；笼统把旧记录全计为新调用则可能重复收费或直接拒绝可恢复工作。

**最小修订：** 恢复只继承从本次冻结根仍可验证、当前编译能力允许的成功只读收据；沿冻结的精确引用链验证，不重猜 latest，不继承 current/审查/执行资格。失去根或权限的旧收据保留为历史诊断，不开放其别名或后续引用。定义累计唯一原件字节、请求次数、实际返回字节/时间在同一恢复链中的承接规则及并发预留边界；重复同 Ref 不再次收取唯一材料成本，但实际重复读取/返回仍消耗请求和IO额度。失败/崩溃预留不得释放成可无限重试的额度。

反例：A→B→C恢复后仍可用；移除根A或改变能力后旧C不能作新读取跳板；多次恢复不能重置累计限额；并发读取相同/不同Ref不会突破限额，且失败不会产生成功来源。

## 已成立的边界与最小实现范围

原报告沿精确生产关联定位 manifest，工具产物从原 Run 正式封存记录反查并核对 Ref，已经解决前版父链方向问题；须坚持完成态和实际封存记录，不能只信标签。历史原字节、别名作用域和资格保持不变，未知不猜最新，成立。

复用已接受计算请求、完整受控执行记录可以免二次填表；任意 shell 缺记录首版保留显式输入是恰当收窄。直接引用由声明提取器生成，控制层不判断科学必要性，也不替科学审查作结论，成立。

有界目录/返回、禁止自动递归、累计原件大小计量具备控制token和IO的基础；实际收益仍需原生对照，不能只凭页小宣称总消耗下降。新增能力是受声明的运行期取证渠道，其“只读”只表示不改原对象，不表示无需来源准入合同。

建议只补上述收据语义及消费者责任表，不重新引入用途依赖数据库、自动输入闭合、日常依赖表或通用历史补关系。若无法在现有manifest/收据边界安全实现，按计划保留显式绑定路径。WP1开发生命周期修复可独立进行；新读取能力须待本计划及WP0精确合同通过后再实现。
