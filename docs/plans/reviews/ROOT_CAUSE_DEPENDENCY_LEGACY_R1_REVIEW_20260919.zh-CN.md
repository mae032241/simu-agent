## 唯一剩余阻断：工具产物与 primary 的 manifest 关系方向不同

R1 WP2“稳定引用”要求“只接受原成果父链中精确同生产者manifest”，但同表“生产关系”同时支持本 Run 的工具产物作为 subject。前者不能无区别用于后者。

当前代码：

- `service/tool_evidence.py:417` 先登记工具产物，parents 为已知输入/来源；记录中保存该工具产物 Ref。
- 同文件 `:504` 的 `_evidence_manifest` 后登记 manifest，其 parents **包含工具产物**，不是工具产物的父对象。
- `operations/input_validation.py:159` 的“manifest 在原报告 parents 中且同 producer”约束针对 `prior_analysis` 报告配对，不能直接泛化给工具产物。
- `service/runs.py:894` 已有精确产物→生产 Run 的查询路径；`:1459` 在正式封存时从 primary 父链取得该 Run 的 manifest。这些现有事实足够构造校验，不需要全库倒查或新权威。

可达反例：下游选择某次已完成分析的工具产物（表格/算法文件/计算记录）作为根成果。该产物已登记可靠用途关系，但其 manifest 是后产生的后继对象；按 R1 字面规则会拒绝，或迫使实现偷偷改父链/放松规则。

**最小修订：** 区分配对入口，身份仍只认原生产 Run 的正式封存事实：

1. primary/旧分析报告保留“父链中的精确同生产者 manifest”检查。
2. 工具产物先验证精确 Ref 属于其原生产 Run 的已登记输出，再从该 Run 的正式封存 primary 找到精确 manifest，验证其 records/bindings 包含该工具产物 Ref；拒绝仅凭 producer label、任意后来同名 manifest 或其他 Run 的记录配对。原产物 parents 不变。
3. 没有可验证正式配对时回到已有显式材料/缺口路径，不猜最新 manifest，不临时扩大权限。

补一个反例即可：已完成 Run 的工具产物作为根成果可找到原 manifest；别的 Run 或未正式封存的 manifest 不能冒充它。生产结果形态若更窄，也可明确首版仅自动消费 primary，但应同步删除对工具产物自动根消费的歧义。
