## P1：展开后的 normalized_request 与显式请求没有可验证的区分

位置：B 首版合同表“冻结与重试”行，尤其“preflight返回包含展开绑定的normalized_request，invoke不再重新展开；其已有指纹/校验语义必须在同一修改中覆盖”。

当前事实：

- `interfaces/mcp_root.py:130–155` 的 OperationInputSelection/OperationCallInput 只有普通 port/artifact_names 输入选择，没有显式根集合、解析快照或控制签发证明。
- `interfaces/mcp_root_operation_routes.py:211–233` 的 normalized_request 是规范化后的普通请求，主要冻结执行配置；没有一个已存在的受验证依赖快照供复用。
- `_prepare_operation_call:1057` 重新按普通选择解析来源；现有 Run 的最终指纹绑定实际完整输入，但首次 preflight 尚未创建该 Run。最终指纹不能反向证明首次调用提交的展开集完整。

因此按 R1 字面跳过 invoke 解析有两种风险：若由客户端标记“已展开”，普通调用可伪装成展开请求并遗漏必需来源；若依据输入长相判断，普通显式附件与自动依赖无法区分，且 normalized_request 重试可能被当作不同显式请求，与同名冻结复用承诺冲突。只写“覆盖既有指纹语义”还没有定义这个新增信任边界。

最小修订优先选择：

1. normalized_request 保持**显式根选择**及配置；preflight 调用与 invoke 共用的纯解析函数作验证，展开结果另作有界预览，不作为调用方可声明的跳过标志。
2. 首次 invoke 从精确不可变 manifest 确定性解析并准入，然后冻结完整集合；不要求先调用 preflight。只有用户确实先做 preflight 时才重复这项有限的机械解析，不是再次执行整个科研行为。
3. 同名重试先核验保存的显式请求及完整配置身份，再使用该 Run 已冻结的集合；不得依赖调用方提交的展开列表推断原选择。创建前的 currentness/资格等仍在 invoke 检查，preflight 从来不是授权。

若必须“解析一次”，需明确另一个方案：返回绑定显式请求、展开集合、解析器/编译身份的受验证快照，并在 invoke 校验来源、完整性及当时准入；这会新增协议与生命周期负担，不是本包的首选。不能仅附一个调用方也能自行计算的 hash 后跳过必要关系校验。

验收补一组真实 Root 入口反例：普通显式调用、原样 preflight→invoke、篡改/遗漏展开预览、两种路径的同名重试。正常路径绑定结果相同，篡改不能省去依赖；合同漂移明确拒绝或成为新调用，不静默复用。

## 已关闭的 R0 问题

**关系及消费范围已有可实施首版。** dependencies 独立于 read_sources/parents，绑定局部来源身份；primary 只包含明确归属的发布组，历史缺关系与新发布fixture分开。现有 `accept_tool_evidence` 已接收 derived_from，并将来源解析为精确引用；`analysis_files.py` 发布脚本及产物时已传 source_aliases。允许对宽泛来源另加可选 reproduce 选择，能避免把所有实际读取变成语义必需。这里不要求工具替科学作者证明有效性。

**端口/预算边界已具体。** 指定消费策略、已有 evidence_inventory 端口、8项/2跳及定向基数调整，保留单项/总量与权限检查，没有隐藏附件。TCAD author 的 CURRENT_PROGRESS_INPUT 确为 max_items=4、2 MiB、on_demand/evidence_inventory（`plugin.py:451`附近）；假设反馈同样已有该通道。实施前精确注册项清单仍必须完成，不能把表中的“等”扩展为任意端口。

**别名与身份区分已足够支持计划层放行。** 源产物精确身份加生产alias解释域，与本轮无控制身份映射分开；不同身份相同字节不合并，历史正文不改写。该方案没有要求 Worker 持有 ArtifactRef。实现验收仍须覆盖一份成果内部映射及多个成果各自同名alias的冲突，不能扁平合并。

**历史合同承诺已纠正。** §4 与 `runs.py::_compiled` 的当前 version/digest 严格匹配一致。旧结果可读与旧Run可执行分开；迁移走新Run准入；不需要多版本解释器；回滚不承诺旧代码理解新schema。
