# 用途依赖与旧引用实施逻辑独立审查

结论：**REVISE**。通用方向正确，现有 Artifact、ToolEvidenceManifest、Run 足以承载首版，不需要依赖数据库或历史迁移；但 WP2 尚不足以直接实施。下列问题属于实施前必须冻结的合同，不能留给编码时临时决定。WP1 的独立边界修复不因这些问题失效。

审查对象为《从根因修复交接与职责边界：实施计划 R0》，SHA-256 `3b8185939f36963d7fac2bb6941915436167baae22cdd81cfe51dcfe9e3c16c0`；根因依据摘要 `f463187b81713e929c071edc982d256b6f5d8f0d0dbdd8135fcad073bd98140d`。核查的是 HEAD `943c4626f8490530e9318eb9fbb409d2670908b9` 上的当前脏工作区代码，不把 HEAD 当作工作区身份。参考跨边界审查及简化技能、架构、设计宪章与约束登记。仅静态审查；未运行测试、科研 MCP、仿真或部署，未恢复 Fig4。其他文档入口与版本一致性由父审查负责。

## 阻断一：历史补登记尚未定义选用与授权，容易形成第二个有效依赖权威

**位置：计划 WP2“生产关系”“历史策略”。** “subject 为已登记产物”“新增不可变记录”只解决不覆盖旧字节，尚未解决同一旧成果出现两份不同关系声明后，下游凭什么选其中一份。若自动找最新记录，则新登记能悄悄改变旧成果的有效依赖；若所有记录合并，则把来源历史误变成必需输入。两者都违反本计划的用途选择和不猜 latest 原则。

真实代码的发布权限是运行中 Run 的已编译工具权限：`service/tool_evidence.py:356` 的 `accept_tool_evidence` 验证工具证据能力、当前输入/证据别名并登记精确父链；`:443` 的 `_evidence_snapshot` 只汇集该 Run 的 bindings/records/attempts；`:504` 的 `_evidence_manifest` 生成该 Run 自己的 manifest。当前没有“任意已登记对象可被当前 Worker 补写关系”的授权。历史物件在库中存在并不等于当前任务有权针对它声明新关系。

同时，`operations/input_validation.py:143` 的 `prior_analysis_sources` 要求 manifest 属于原报告 parents，且同一 producer Run。新登记的 manifest 无法通过这条原始作用域配对检查；不能为了支持新增关系而削弱此检查。新关系说明的是新的依赖断言，不是重新证明旧正文里 alias 的含义。

**最小修订：**

- 历史补登记必须在现有、具备发布能力的新 Run 内进行；subject 与依赖均须是该 Run 已授权绑定或本 Run 已登记的对象。历史确需一次性补证时，复用当前任务的显式科学材料选择，控制层填精确 Ref；这不能变成每次发布额外填写的依赖表。关系生产入口及其适用权限必须列入 WP0 表。
- 补登记记录随新 manifest/产物封存，保留生产者、用途及依据入口；原 Artifact 和 parents 不变。声明真实科学必要性由 Worker 或确知计算请求的领域工具负责；控制层只校验身份、作用域、权限和结构，不替 Worker 判定关系科学正确。
- 普通新产物只消费其精确生产 manifest；旧产物的补充关系须由本次请求显式选择精确新记录，并通过声明端口准入。若要免显式选择，必须先提出另一种唯一、不可变选择依据并独立审查，不能以全库反查或 latest 实现。
- 本次选定关系记录的 Ref、subject、用途和解析结果进入同一个冻结 Run 请求。记录变更必须成为新对象及新请求，不能覆盖“当前关系”；多份冲突记录无明确选择时拒绝并定位冲突。
- 原始 alias 解释域与补充依赖断言分开。新增记录不能补造缺失的旧 alias 身份、替换原 manifest、继承旧资格或使原 claim 自动重新合格。

验收反例：相同 subject 有 R1/R2 两份不同补充关系；显式选择 R1 的 Run 不受 R2 发布影响；未选择时不能自动选 R2；未绑定 subject 的 Worker 不能补登记；新 manifest 不能冒充原报告 manifest。

## 阻断二：共享来源复用与端口准入尚无确定组合规则

**位置：计划 WP2“消费策略”“预算”及共享依赖段。** 当前 `operations/invoke.py:166` 起的 `preflight_operation` 全局按 ArtifactRef 去重，并以 `input_artifact_duplicate` 拒绝第二次绑定；每个绑定只有一个 port/usage/exposure。`:354` 的 `_validate_port_binding` 按各端口分别检查数量、schema、media type、单件大小和 current。故“重合精确来源复用”不能直接等同于将不同端口的条目删除。

可达场景：某原件已经显式绑定为受信证据，同时又是根成果复算所需 inventory 依赖；或两个根成果为相同原件指定不同目的端口。直接追加会被拒绝；粗略去重可能移走受信端口、破坏最小数量，或把背景可读性误当资格。这是端口语义问题，不应靠统一扩容解决。

**最小修订：** 首版保留一 Ref 一个实际绑定。明确同一目标端口重复引用复用现有绑定；已有显式绑定可满足自动依赖的条件须由编译策略规定，保留显式端口及其所有准入要求；无法兼容的跨端口要求给明确冲突，不静默移端口。若确实需要多端口逻辑绑定，则单独设计其校验与计费规则，不能只删除 duplicate 检查。

预算同时覆盖完整有效输入、端口数量/单件限制、manifest 及关系索引本身、解析访问规模；按需读取不免除完整输入准入预算。物理字节去重与逻辑端口资格须分别说明。没有合法端口的 Operation 先明确修改合同或保留可定位缺口，不隐式开附件通道。

验收反例：菱形依赖正常复用；跨端口不兼容明确拒绝；受信端口仍独立校验；大原件即使只投影一行索引也触发实际输入预算；回边循环区别于共享来源。

## 阻断三：幂等冻结仍缺选择身份与有效身份的完整落点

**位置：计划 WP2“幂等冻结”“preflight”。** 当前 `mcp_root_operation_routes.py:355` 的 `_prepare_local_run` 以已展开 bound inputs、编译 digest、执行 profile、instruction、恢复/草稿等计算 fingerprint 后才查创建目标；`service/runs.py:278` 的 request digest 再绑定冻结 inputs、后端和 limits。不能仅在 invoke 开头比较原始 JSON 相同就返回旧 Run，也不能只把展开后的输入加入旧 fingerprint 后重新查找。

尤其前述新增关系会出现“有效依赖相同、声明依据不同”的情况；若只冻结来源文件集合，无法证明本次究竟采用哪个关系记录。反过来，若每次先解析新记录再比较，同名重试会被后来的关系影响。

**最小修订：** 在现有 Run request 内明确持久化规范化显式选择和有效冻结输入的区别，并给出比较顺序：先比对包含精确根来源、显式关系选择、Operation 版本/digest、指令、profile 与恢复/预算选项的显式身份；匹配已存请求才复用其冻结证据。首次创建解析精确不可变关系，连同关系证据 Ref、用途、别名映射及有效绑定纳入 request 身份。别名/名称解析的语义必须明确，不把同一文本名称重新绑定后的不同来源误认为同一请求。

preflight 可以预览，但 invoke 必须重新验证预览所依据的精确选择；客户端展开集合不能成为权威。两个并发同名调用需要沿已有创建幂等边界保证单一冻结结果；失败重试不能生成另一份依赖快照。版本不匹配只允许读取旧结果，不能借“幂等命中”续接不兼容执行。

无需新建状态表；需要在计划中明确现有 request 的序列化/恢复消费者也同步修改。验收应覆盖同名同请求、改变关系选择但有效文件相同、名称重绑定、并发创建、崩溃后重试、部署版本改变及预览到创建之间的变化。

## 旧 alias 的可行实现与剩余验收

现有 `prior_analysis_sources` 已能从精确配对 manifest 的 binding 将旧 alias 映射到当前相同 Ref 的别名；旧 manifest 缺少 bindings 时只认可有证据的 records，不能恢复未登记输入。此实现可复用，但目前是单一 prior_analysis 配对；`service/run_assignment.py:97` 的 `prior_source_bindings` 是平面映射。多旧成果场景应改成以当前根成果 source_name 为作用域的投影，再容纳各自旧 alias，内部保留原生产 Run/manifest 身份，不向 Worker 暴露控制身份。

当前映射只加入已绑定匹配项，未匹配项被省略（`input_validation.py:183` 起）。计划要求“未知/歧义明确”时必须投影其状态：至少区分已有精确身份但本次未带入、原作用域记录缺失、作用域不匹配/歧义；不能把所有缺失统一解释为“不存在依赖”。旧正文保持原字节，Worker 按根成果作用域读取映射；一份旧报告里的 `tool_evidence_001` 不得覆盖另一份旧报告中的同名引用。

此外，当前 manifest 在 primary 封存链中作为前序证据。用途关系若 subject 指向“本次 primary”，应使用本 Run 声明的 primary 槽位并在封存时校验绑定，不把尚未产生的 primary Ref 写回其父 manifest 形成内容身份循环。已登记 subject 则用精确 Ref。应在 WP2 设计审查中明确这个区别。

## 阻断四：发布合同不能把机械交接重新变成 Agent 填表

**位置：计划 WP2“自动登记”中“自写脚本通过现有发布入口选择材料及用途”。** 该表述仍允许实现为发布时要求 Agent 回忆并填写依赖列表，未消除本轮目标中的机械负担。现有 `analysis_artifacts.py:15` 的 `publish_analysis_file` 接受 sources，`:26` 的 `retain_calculation` 已从 CalculationRecord 的 input_digests 得到部分来源；应沿计算请求/执行事实复用信息，不再新增一份 Agent 手填依赖清单。

**最小修订：** 框架计算工具直接从已接受的算法、输入、参数与输出映射登记用途关系；受控启动的自写脚本复用启动时明确的输入与执行记录，把关系关联到该次产物，无须发布后重新填写。执行记录只能证明实际使用事实；“读取过”不能自动升级为审查/复算语义必需，必要性由已有计算合同和科学任务选择界定。无受控执行记录的脚本/历史材料保持显式绑定或有依据的一次性补证，不能宣传全部自动闭合，也不能增加日常表格。

验收应观察实际 Worker 发布工具合同：原本算法/输入/参数已经确定的计算不得再次要求依赖字段；无关读取不加入必要集合；无执行记录时返回可定位缺口，不能从文件访问日志或所有 read_sources 猜科学必要性。

## 允许保留的最小方案

保留既有发布、manifest、Run 请求、端口准入及 assignment 路径；关系字段只表达用途化必要性，不复制 current、资格或执行状态。Artifact parents 保持来源证据，不能升格为默认依赖集合。assignment 是冻结输入的可重建索引，不能反向改变 request。新发布闭合用新 fixture 验证；旧引用用原作用域 fixture 验证；历史新增关系另用显式选择 fixture 验证，三者不可互相替代。

以上修订不需要全库迁移、不需要新科学调度角色、不需要自动补历史资格，也不需要全面重构。完成这些合同并独立审查后，才足以对 WP2 给出可实施 PASS；本审查不把方向正确等同于源码已实现或生产验证通过。
