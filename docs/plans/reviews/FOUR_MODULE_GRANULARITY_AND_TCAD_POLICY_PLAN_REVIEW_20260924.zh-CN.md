## 2. 通过依据

### 2.1 颗粒度已成为实际首批目标

主计划第 30–34、132–134 行和细节计划第 38–70、122–136 行，明确把两个科学作者合为一个 Run，工具计算放进该 Run，独立 audit 继续独立。验收禁止后台保留第二作者或串联微任务。Root 字段投影、自动绑定和 native 派发均不再是合并的前置条件。

这与当前真实调用链对应：`figure_science_operations.py:OPERATIONS` 存在 request 与 Intake 作者；`FIGURE_FAMILY_REQUIREMENT` 和 `operation_transforms.py:figure_parentage` 要求旧 Transform 来源族。细节计划没有简单删除这些检查，而是安排新工具记录、新审查和 bundle 消费关系同批闭合，旧关系保留原身份。没有发现仅在原链外加模块包装的设计。

首批限定栅格单 panel、已有算法和有限系列；复用 `tool_evidence`、恢复及 normalizer。主计划没有另造 ModuleRun、固定 DAG 或第二套状态机。假设保留独立 critic，分析复用已有连续工具能力，未为了凑四个模块重写成熟路径。

### 2.2 额度内免人工审批是完整政策调整

主计划第 65–93、99–101、121–128 行覆盖配置、编译声明、preflight/invoke、Execution 授权和部署规范。默认目标值明确为十进制 `2_000_000_000` 字节和 `3600` 秒，包含等号；开关、阈值和超额处理配置化；缺配置不静默授予权限，但交付的目标部署必须显式启用。

当前 `plugin.py:tcad.study.execute` 声明 `ApprovalContract`，Root `_invoke_compiled_effect()` 无条件调用 `_ensure_execution_approval()`，`ExecutionService.authorize()` 读取 `HumanDecision`。计划已明确需要改这些真实阻断点，沿同一 Execution 生命周期记录 `policy` 或 `human` 授权，没有通过伪造人工决定实现免审批。

计划同时要求提交前核对有效策略、未提交请求受配置收紧影响、运行中任务保持冻结上限、未知提交权威查回。这些安排保护精确对象和幂等副作用，没有因免审批而删除它们。已有科学审查仍适用，但禁止新增等价的人工作为低额度执行前置条件。未发现“口头放开、计划仍强制弹审批”的矛盾。

### 2.3 资源闭合与交付成本基本自洽

主计划第 54–59、103–115、138–144 行区分存储与 RAM、逻辑产物与暂存磁盘、solver 墙钟与收集超时，并要求同一 study 的成员共享预算，恢复不重置额度。`ResourceLimits` 目前只有 `max_output_bytes`；runner 的 `RLIMIT_FSIZE` 只能约束单文件。计划正确识别总存储需要补充，未把提高输出常量误当总量限制。

远端示例目前 `max_transfer_bytes=536870912`；计划将其和本地存储、CAS、打包、收集、分析读取一起纳入验收。2GB 数据要求流式传递和摘要校验，不能 JSON/base64 或整块加载。小额度负例、超过旧上限的真实文件和一次短真实 solver 正例，能覆盖直接风险；没有要求等待一小时或重跑全部历史测试。

采样监测允许超调且必须如实报告，第 107 行明确不等同硬配额。因此第 155 行“额度强制执行”应依前文理解为超限检测及终止，不能在实施报告中改称物理占用绝不超过阈值。采用这种首版能力不构成计划阻断。

首批 B 跨越多个模块，工作量明显大于改一个 approval 分支，但这些边界直接来自用户的配置和容量要求。A、B 独立交付，不使颗粒度改革等待全局执行重构。未发现必须先建设通用调度平台才能实施的要求。

### 2.4 发布和回退没有继承旧合同的虚假承诺

`RunService._compiled()` 当前拒绝 version/digest 漂移；主计划第 152–154 行和细节计划第 7 节要求排空受影响任务，不承诺旧 assignment 跨版本继续。回退保留新记录并先验证可读，不能把 policy 记录转为假的人工批准。计划清楚区分历史可读、计划 PASS 和真实执行验收。

## 3. 非阻断实施注意项

以下不是要求另开计划或先返工送审；可写入同一实施记录，在对应代码实施和验收时关闭。

### N1 / P2：明确把开发调试的实际限额消费者纳入精确 diff

- **定位**：主计划第 107、121–126、153 行；`plugins/tcad_artifact/tcad_artifact/debug_adapter.py:37` 的 `_PREFLIGHT_WALL_SECONDS`、`_SMOKE_WALL_SECONDS`、`_INITIALIZATION_WALL_SECONDS`，以及 `local_debug_service.py:39` 的 `_MAX_RUNS`、`_TOTAL_WALL_SECONDS`。
- **可达场景**：只完成表格内列出的生产 Execution 和两个 runner，作者仍通过现有 development debug 工具执行，时间继续被 60/180/120 秒及总 360 秒的旧常量收窄。
- **要求和影响**：用户要求相关执行额度可配置；主计划已禁止旧低额度硬编码替代自主范围。漏掉这些实际调用者，会造成生产执行配置生效而开发诊断仍有不可配置的隐藏边界。
- **最小落实**：实施记录显式列入 `debug_adapter.py`、`local_debug_service.py` 的相关消费者，区分任务请求、诊断总预算和作者 Run deadline；领域诊断确需更小限额时同样来自明确配置并向 Agent 展示。无需取消有界尝试机制，也无需把返回文本大小等无关常量都统一成 2GB。
- **关闭条件**：两组配置从实际开发工具入口产生一致的可见限额与生效限额；达到任一独立预算时准确说明是哪一层限制。主计划第 153 行已提出这项要求，故不是计划缺失或阻断。

### N2 / P3：采样高水位不能命名为完整实际峰值

- **定位**：主计划第 107、142 行“实际峰值与超调”。
- **可达场景**：solver 在两次目录采样之间快速写入后删除文件；轮询记录不到那次瞬时占用。
- **要求和影响**：计划允许采样超调，但如果报告把最高采样值标成完整真实峰值，会夸大监测证据能证明的容量上界。
- **最小落实**：实施记录使用“观测高水位/观测超调”，同时记录采样间隔、终止宽限和未观测瞬时峰值的限制。后端提供真实配额或权威高水位时，再按相应证据报告。
- **关闭条件**：目录暴涨负例的报告明确采样能与不能证明什么；不要求为此新建配额系统，不影响额度内无需人工审批的授权路径。

## 4. 结论的边界

本次没有发现需要退回修订的计划级问题。建议直接按 A、B 各自的精确候选实施，相关负例合并验证，避免为上述注意项再拆出审查链。

仍待实现验证的是：完整工具证据族可被独立 audit 与 bundle 消费；失败恢复不重算；policy 授权确实跨全部实际入口生效；同一任务预算在多成员和恢复时连续；本地/远端流式大文件可达；配置收紧及未知提交恢复保持一致。这些已经写入送审计划的交付条件，不能因本次计划 PASS 而略过。
