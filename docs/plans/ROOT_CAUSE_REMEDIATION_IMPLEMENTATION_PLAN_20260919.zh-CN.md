本计划替代 [全局整改R2](GLOBAL_HANDOFF_AND_CONTEXT_REMEDIATION_PLAN_20260919.zh-CN.md)作为下一轮设计入口；R2审查PASS仅适用于其历史文本，不能继承为本计划PASS。依据为 [根因再分析](GLOBAL_HANDOFF_ROOT_CAUSE_REASSESSMENT_20260919.zh-CN.md) 和 [本轮观测](evidence/fig4-handoff-context-20260919/OBSERVATIONS.zh-CN.md)。保留已有原件、测试与审查，不重写历史结论。

## 一、目标：保证任务可交接，而非保证Agent永不犯错

当前缺陷不是没有Artifact、Operation或Schema，而是组合后缺少一致语义：产物的来源不等于下游必需材料；开发候选不是最终成果；工作诊断不是不可变输入；可保存信息不等于应进入模型的信息。

本次完成标准：Root选择科学对象与任务后，控制层能够准确准备该用途下已知的必要材料；Worker知道当前任务、目标、能力及限制，能独立工作或交付明确缺口；正常纠错不被工程错误挡住；Root不再为机械交接阅读全文找文件。

| 保留主体 | 必须承担 | 必须移走或避免 |
|---|---|---|
| Root | 依据正式结果选择研究方向、对象、预算与下一动作 | 逐个搬运已登记依赖；靠自由文本恢复临时别名 |
| 科学Worker | 科学解释、方法、条件、相关证据选择和结论范围 | 手填控制身份/哈希；替控制层修派生字段；自己批准执行 |
| 控制层 | 已知依赖解析、稳定引用、冻结绑定、任务视图、权限和事件记录 | 推断未知科学关系；根据评分替Agent决定机制 |
| 领域组件 | 登记自身确定的输入输出关系，实现并诊断实际计算 | 自建Run/审批状态；把初始化成功当科学完成 |

不新增固定DAG、通用依赖数据库、新科学调度角色、通用执行器、读取登记状态或大量强制科学字段。不改变外部执行审批边界。不以“所有校验删除”代替职责修正。

## 二、三个通用约定

### 约定1：产物在明确用途下可消费

Root仍选择现有Operation和根成果；消费用途由该Operation的编译声明表达，不另建动作注册表。区分：

- 了解当前研究：目标、正式结论、限制和未解决矛盾；原始材料可追查。
- 独立审查：审查对象与支撑其关键判断的原始依据，不能只有作者摘要。
- 复算/实现：对应算法、原数据、参数/边界定义，以及声明的执行能力。

这些是消费语义，不是新的Run状态。一次任务可有多个现有端口分别承担不同用途，不要求所有任务都绑定三套材料。

在现有Artifact/ToolEvidenceManifest上表达“该产物用于某种用途所需的确切来源”；来源/读取历史不自动成为必要依赖。工具已知道的算法和数据关系由工具登记。只有Agent才知道的科学相关性仍由Agent选择，控制层不从代码import、文件名、正文或全父链猜测。

新Worker只看当前source_name及用途/访问入口。历史引用解释在其生产上下文中，控制层维护“原成果中的引用→当前可访问材料”的映射；局部别名不是持久身份。旧正文不改写，历史无法解析的引用如实标记，不猜latest。

### 约定2：动作只要求它实际需要的条件

| 动作 | 检查对象 | 不应要求 |
|---|---|---|
| 输入准入 | 本次冻结输入、用途、权限、预算 | 输出是否已有科学结论 |
| 开发预检 | 当前源码、声明、依赖、求解器能力 | 最终科学summary/verdict |
| 成果封存 | 成果结构、真实引用、声明的输出规则 | 再次判断已准入输入是否应启动 |
| 外部执行 | 精确可执行工程、对应审查与授权 | 把有可读历史当作有效授权 |
| 结果分析 | 实际结果与可支持的结论范围 | 强迫不完整证据产生肯定结论 |

各动作共享相同来源和字段定义，但不共用不适用的完成条件。机械字段从权威来源生成；缺少科学内容不能靠默认“pass”补齐。

记录写入分四种既有语义：不可变输入/封存产物；可改开发草稿；追加尝试诊断；可重建当前摘要。明确每个写入点属于哪类，不新增生命周期管理系统。

### 约定3：记录完整，模型只读当前决策所需视图

默认呈现当前任务、总体目标入口、当前阶段目标、必要材料索引、能力限制和交付要求。完整产物继续可读；按需展开不等于删除信息或只给二手摘要。

同一科学结论只有一处权威表达，handoff/status引用或选择该处，不要求Agent重复填写。服务端机械响应在进入模型前有界；宿主shell/JS不是框架可硬限制的渠道，必须如实保留此限制并通过公共指引与行为验收控制批量展开。

## 三、工作包：每包交付可验证的行为

### WP0：冻结边界与反例，防止再次边做边发明机制

交付一张覆盖所有public Agent Operation及相关Transform/Effect的责任表：输入来源、生成字段、输出规则、依赖生产者/消费者、动作阶段、是否存在多处权威。按共同实现归组，不为每个Operation复制测试。

冻结三条生产反例：算法/原表漏绑；不同失败报告连续写入；开发预检要求最终handoff。另固定一个非TCAD小型分析→审查/复算fixture，证明后续改动不依赖Fig4名称。

记录当前工作区diff/源码摘要、安装指纹、精确输入、模型/effort、预算及计量起止事件。现有HEAD不能替代脏工作区候选身份。此阶段只读核查和fixture准备，不运行生产仿真。

放行：每个改动能对应至少一条可重现失败和唯一责任边界；无生产证据的“顺手重构”排除。

### WP1：统一开发检查与诊断生命周期

落点：TCAD `operation_workspace.py`、`plugin.py::_debug_tool`；通用 `mcp_local_worker.py`、`result_materialization.py`、现有Run错误记录路径。

1. 开发preflight只读取候选工程所需内容，移除对最终科学handoff的无关前置要求；最终提交仍要求真正科学交付或明确implementation_gap。
2. 控制层生成字段在单一材料化边界生成，模板/Schema/预检/提交消费同一定义；不能为模板不完整让Worker猜字段。
3. 运行中材料化报告用可更新派生记录语义；保留每次尝试的具体诊断。封存产物与输入保持不可变，符号链接和越界保护不放松。
4. 异常首次被掌握时登记一次，后续层引用原事件；尚未登记的错误补完整事实，不简单删除所有记录。事件应区分开发预检拒绝、成果拒绝、求解器错误、超时与控制层故障。
5. 沿共用调用边界检查同类模板/写入/记录缺陷，一并修复实际生产路径；不按TCAD错误字符串打特判。

验收：缺科学summary不妨碍合法开发预检；缺最终科学交付仍不能冒充completed成果；连续失败A/B再成功，A/B原诊断可读且各计一次；报告写失败不掩盖原错；已有不可变证据不可被替换。

### WP2：控制层接管已知依赖交接和引用映射

落点：`operations/spec.py`及编译层、`operations/invoke.py`、`mcp_root_operation_routes.py`、`service/tool_evidence.py`、`analysis_artifacts.py`、`run_assignment.py`；域发布入口只声明其自身确知关系。

首版只处理已接受计算请求或受控执行记录所能证明的关系，不覆盖任意隐式依赖、不新增日常依赖填表、不提供“给任意历史产物补关系”的入口。采用如下合同：

| 项目 | 实施要求 |
|---|---|
| 生产关系 | 在现有manifest增加可选用途化关系，只由本Run已编译授权工具登记。本次primary以声明的output槽位表示，seal时核对归属，不在父manifest中回填尚未产生的primary Ref形成身份循环；其他subject仅限本Run已登记的工具产物。来源限本Run已授权输入/工具产物，精确Ref由控制层保存。 |
| 自动登记 | 框架计算工具直接复用已接受请求的算法、输入、参数及输出映射，不要求调用者在发布时再次提供sources/依赖表。受控脚本只在已有启动请求完整声明输入和输出关联时复用该执行记录；不为任意shell新增追踪器，不从文件访问日志推断。已有计算合同确定复算所需关系，实际读取只作来源事实；不把无关读取升级为审查/复算必需。 |
| 无记录材料 | 普通shell产物、历史文件或不完整执行记录沿现有显式绑定/发布路径使用；不声称自动闭合、不新增必填依赖字段。已知具体依赖未提供时给可定位缺口；没有关系记录仅表示未知，不将所有历史成果一律拒绝。 |
| 消费策略 | 在现有Operation编译定义中声明哪些根输入按何用途消费、依赖进入哪个既有inventory端口；不存在合法端口时先修改该合同并版本化，不暗塞附件。 |
| 预算 | 保留一Ref一个实际绑定；完整有效输入计入现有端口数量、单项字节和任务总字节。关系manifest和映射本身另计其实际准入/投影预算，解析访问规模有界；按需读取不免除大文件预算。物理去重不能取消端口资格。容量调整须有fixture证据，取消统一4→12扩容。超限返回需求和缺口，不挤掉显式输入。 |
| 来源权限 | 依赖可读不意味着具有claim资格；不能通过背景端口满足审批或受信证据条件；跨实例/越权限依赖不得自动补入。 |
| 稳定引用 | 新输出仍用可见科学别名，其解释域是原生产绑定。只接受原成果父链中精确同生产者manifest，复用现有配对检查。assignment按根成果当前source_name分组展示旧alias→当前alias，不用平面映射覆盖多个原作用域；不向Worker暴露控制ID/哈希。 |
| 幂等冻结 | 现有request持久化规范化显式选择及完整有效绑定两部分；显式身份和有效身份的比较顺序见下节。关系证据Ref、用途、映射及解析版本均进入冻结身份，不只保存最终文件集合。同步修改现有request序列化/恢复消费者，不另建表。 |
| preflight | 只返回规范化显式请求并可预览解析；invoke按同一纯解析逻辑核查不可变关系并在创建时冻结，不信任客户端声称的展开集合，不强制双调用。 |

**端口复用的确定规则。** 保留现有跨端口重复Ref拒绝，不删除该检查。自动解析前对来源去重：

1. 同一目标端口已有相同Ref，复用该绑定，不增加条目。
2. 其他端口已有显式Ref，仅当编译策略明确允许其可读投影满足本次inventory用途、且没有额外schema/media/current要求时，保留原显式端口与全部准入校验，通过映射供依赖访问；不移端口、不创建第二绑定。该复用不计算目标端口的必需最小项数，不把背景材料提升为claim。
3. 多个自动根共享来源，目标端口一致则合并；目标端口不一致且没有明确兼容策略则报告具体冲突，不任意选择较宽端口。需要多端口逻辑绑定的情况不纳入首版。
4. 菱形共享依赖正常复用，只有递归路径回边才是循环。解析规模受现有任务预算与显式编译限制约束，不以Fig4数量定义通用原则。

**请求身份与创建顺序。** 首次/重试都先将显式语义名称解析为本实例精确Ref，不能只比较相同JSON或名称字符串。显式身份包括这些Ref、Operation version/digest、instruction、执行profile、resume/draft及其身份、尝试预算等已有行为选项。查同名已存调用：身份匹配且当前合同可用，复用已存有效集合；不匹配沿现有reject/create_revision处理。首次创建才解析根成果各自的精确生产manifest，将关系证据Ref、消费用途、原作用域映射、有效输入、解析版本纳入现有request摘要与Run创建事务。相同文件来自不同关系证据也不是相同有效请求。并发同名调用沿既有唯一创建/幂等机制只产生一个冻结Run，崩溃后从已存请求恢复，不重建另一份集合。合同漂移时只允许历史读取，不借幂等命中继续旧Run。

可选preflight规范化显式根输入、返回预览，invoke核对实际精确来源及当前资格；不信任客户端附送的“已展开绑定”。两者共用纯解析函数，但不要求调用两次。资格改变在实际创建动作准确报告，不挪到最终输出校验。

**历史策略收窄。** 首版取消通用历史补登记功能，避免为旧成果创建第二个“有效依赖”权威。旧产物和原manifest保持不变：已有可信生产绑定可用于alias解析；没有用途关系时继续显式绑定必要原件，不全库反查、不自动选最新关系、不合并多份推测。需要一次性重新建立可复用材料时，只能在已获授权的新研究Run内实际使用明确输入，产生该Run自己的新产物和manifest；它不是原产物的替代manifest，也不重证明旧alias。将来若确有历史补关系需求，须另审显式选择、生产权限与冲突合同，不能顺手加入本包。

映射状态必须区分：原来源身份明确但本次未带入；原生产记录缺失；生产作用域不匹配/歧义。无匹配项不能静默省略成“没有依赖”。数据可读与用途资格保持分离，原科学正文不改写。

验收：Root仅选择成果/Operation，下游能取得确切算法与原表；重排别名/换Worker/新Run不改变引用；同名重试不因后来材料变化漂移；缺失、权限、容量和历史歧义定位准确。审查与复算按用途得到各自需要的材料，不自动全文展开全部历史。

上述自动取得仅适用于已有可靠关系的新产物。必须分别执行这些反例：

- 新计算发布不再次要求依赖字段；无关读取不进入必要集合；无完整执行记录仍可显式使用，不虚报自动闭合。
- 两旧成果共享同名alias不冲突；新manifest不能冒充旧报告manifest；未绑定的历史subject不能被工具补登记。
- 同目标端口菱形依赖去重；不兼容跨端口冲突明确；受信端口资格仍独立校验；大原件即使只显示索引也计入预算。
- 同名同请求、名称重绑定、关系证据改变但有效文件相同、并发创建、崩溃重试、部署digest改变、preflight到invoke期间变化分别验证。
- primary槽位在seal时正确关联，不出现primary↔父manifest内容身份循环。

WP2设计审查交付物必须包含精确schema增量、消费策略注册项、request序列化变更和上述反例映射；未确认任何一项，不进入实现，不靠编码时临时扩展合同解决。

### WP3：能力信息进入任务准备，避免不可交付设计

落点：Operation目录与域execution capability的现有投影、`general_science_*operations.py`、`general_science_resources.py`、scheduler指南。

从单一注册事实投影可调度动作、运行边界和能力来源。区分“分析既有结果”“开发诊断”“执行新实验”；明确已声明能力、需作者实测验证、尚不存在的能力。运行可用性是带时点事实，不能当永久授权。

设计者交付实现必需的科学定义；作者负责源码和具体接口可行性；审查者只要求当前阶段必须解决的内容。缺口结果通过现有artifact/review/revision路径返回，Root决定下一动作，不添加固定回退路由。

验收：同样输入不再承诺未注册的一维执行；作者无须发明未确定的科学参数；计划审查不会要求未开始实现就交出初始化证据；能力失败不会变成机制反证。没有新执行器开发。

### WP4：建立按用途的决策视图，减少重复携带

落点：Root MCP响应投影、`run_assignment.py`、`input_reader.py`、`mcp_local_worker.py`、`platforms/codex.py`及科学结果物化/读取路径。

1. Root需要的状态、科学结论、限制、矛盾和下一步理由一次选读；机读绑定留在编排存储，原件直接传给Worker。不同schema的字段导航由同一编译产物定义提供，不让Root猜字段。
2. 审计formal payload、handoff、scheduler_signal、status、UI/CLI重复字段；机械副本投影生成，科学结论保持一个权威位置。缩减不能丢错误、分页、省略标记和原件入口。
3. 单次工具返回和批量编排整体都需限制无目的展开；框架服务端能约束的就在那里处理，native shell只能做指引和可观察验收，不伪称全局硬封顶。大原件按字段/段落定位，不循环读尽再统一打印。
4. 复用Worker只重读变化内容、当前任务和缺失上下文；不建立模型“已读账本”，不认为输入hash相同就证明模型记得。独立审查不能复用作者。
5. 完整报告结构的删减必须找实际消费者。先移除机械复制，必要科学条件/公式/验证方法保留单一引用；不为了变短删掉原目标或降低审查质量。

验收：固定交接同科学要求下Root额外阅读和峰值下降；Worker没有超量批量打印/重复未变材料；遇到错误仍能精确展开。保持需要大部分原件时一次完整读取的合法路径，不强制每次先目录后全文。

### WP5：跨边界回归、兼容和发布

覆盖按共用路径分组的所有Agent类型、工具发布、Transform、Effect/Approval、恢复、MCP、CLI/UI读视图。相同源事实在各投影含义一致，不要求全部相同篇幅。输出校验不重做输入准入，科学判断不偷偷回到控制层。

兼容状态：已完成Run的封存字节保留；旧运行任务仅当前compiled version/digest完全匹配才续接，不能承诺历史合同执行。新Run重新准入，审批仍绑定精确对象。关系格式/输入语义变化按现有Schema/ABI/Operation版本机制升级；新旧解析路径明确测试，不为兼容引入第二注册表。旧版回滚仅保证其支持schema可读，不能保证消费所有新产物。

发布前核对源码、wheel、服务和生成角色配置一致。未改runner接口不要求同步VM。先做独立实现审查和隔离安装验证，用户授权部署后再测实际入口；不自动继续Fig4。

## 四、验收与资源纪律

先做反例，再修复，再跑相应定向测试；不使用全量测试掩盖生产交接失败。复用现有test_l4_local_tcad、test_contract_attempts、test_tcad_gap_continuation、test_invoke_preflight、test_continuation_input_guidance、test_run_status_output_selection等相关用例，新增只覆盖真正缺陷。

原生行为验收固定三条路径：

1. 分析→假设/设计→独立审查：自动交接用途明确的必要原件。
2. 修订→同reviewer接续：源身份稳定、变化材料可见、未变材料不机械重读。
3. 作者开发失败→纠正→成功或正式gap：错误可定位、记录不重复、失败不伪装科研结论。

至少加入一个不含TCAD字段的同构小任务验证共同机制，不为它创建生产执行器。需要新仿真的科学验收留待用户恢复Fig4。

每组记录精确候选、输入、模型/effort、预算、起止事件、请求数、单请求输入和工具可见字节。Root/Worker分列，初始历史背景一致；用户插话、维护、监控和重试单列；compaction/重启分段。缓存累计仅作成本辅助，不等于窗口。至少两组配对展示波动，不能据小于波动的差异宣称稳定收益。

放行需要功能与成本两条证据：依赖漏绑/引用错配/事件重复为零，异常可定位、独立审查和目标可达性不退化；机械响应不重复展开，原生额外阅读/返工和峰值有改善或明确说明未证明。不得以节省token抵消科学材料遗漏。

本地定向测试串行，沿用768MiB进程树守卫；它不约束模型服务内存。需要超出本机预算的原生探针由用户执行。任何步骤不跑并行全量测试。

## 五、执行顺序与停止条件

顺序：计划独立审查→WP0→WP1→WP2→WP3→WP4→WP5。WP1可独立交付，不等到所有机制完成；WP2有通用关系合同的独立设计审查门，不能在实现中临时扩大权限/端口。每包独立实施复审通过再进入下一包。

实现前若发现必须新增全局状态机、隐藏附件通道或推断科学依赖，停止该包并回到设计，不以临时特判完成。源码变更与历史兼容/权威关系清楚后才部署。

科研恢复是单独阶段：保留现有作者源码、初始化证据和实现缺口，先由合适科学/实现角色判断accepted-step监视接口或等价守恒验证；必要时明确修订计划并独立审查，再沿已有TCAD链执行。控制层不能降低物理验证要求，本工程计划也不自动授权恢复研究。
