# Root 与 Worker 指令分离方案

状态：I1 源码、定向验证及独立复审通过；I2 源码接线已纳入，真实发布资格未完成；尚未部署。基线：dev `6854718`。
本文件只维护本次提示分离的设计、节点与退出条件，逐次证据在独立实施报告。

## 1. 目标与依据

Root 调度规则进入 Root 的角色指令；项目 AGENTS.md 保留共同约束和用户原文；Worker 接收自己的启动规则与冻结任务合同。

已确认：安装器将 scheduler 写入项目 AGENTS.md；s10 的四个 fresh Worker 都收到相同项目说明，同时收到自己的 developer 角色说明。项目正文为 7,838 字符，其中共同约束仍有价值，不能全部算作可删冗余。尚未证明这段提示造成了实际错误动作。

既有上下文修整 `f47c960`、`3ac8abf`、`6854718` 保持有效。本方案只解决角色提示的安装范围；附件阶段封存故障和最佳结果选择错误另行修复。

官方配置提供 developer_instructions；自定义子 Agent 文件作为子会话配置层，可覆盖会话设置。目标 CLI 中是否确实替换父角色文字，仍须在本次验证，而非由文档推定通过。

- [配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)
- [子 Agent 配置](https://learn.chatgpt.com/docs/agent-configuration/subagents)

## 2. 指令所有权

| 内容 | 唯一维护位置 | 接收者 |
|---|---|---|
| 共同科学/控制边界、原件与限制、未知提交处理 | 简短共同模板，生成 AGENTS 托管块 | Root、Worker、helper |
| 用户项目规则 | 用户 AGENTS 的托管块外原文 | 沿平台正常发现规则接收 |
| 实例选择、完整任务调度、派发、审批协调、结果消费 | 现有 scheduler 模板，生成 Root developer 配置 | 受支持入口的 Root |
| 打开 assignment、Worker 工具与交付边界 | 现有受控 Agent TOML 的 developer 指令 | 对应 Worker/helper |
| 当前任务的科学角色、输入、作者表单 | 冻结 assignment / worker-start | 当前任务负责人 |

共同模板只保留真正跨角色的规则；Root 不再每轮复制整份 scheduler。科学阶段职责、原生权限和控制准入维持原实现，不增加角色注册表或科学审批。

### I0：先验证替换，不先删除现有入口

使用独立临时项目与隔离配置，设置三个无敏感信息的唯一标记：Root R、Worker W、用户共同规则 U。观察真实角色消息/有效配置，模型自述仅作补充。

先验证配置与零模型协议能覆盖的部分；native spawn 所需部分使用最小模型回合，串行完成。优先使用 gpt-6.1-sol/high；不执行科学实验、TCAD 或大量子任务。复用现有探针入口，不新建验收框架。

覆盖受控文本/图像能力角色，以及 helper 实际使用的角色路径。模型无需生成图片。非内置插件使用现有能力角色生成机制，用机械夹具覆盖即可。

若实际平台把 R 与 W 叠加，则停止迁移 AGENTS，记录不满足的具体能力；选择经验证的 Root 专属会话入口重新评审。不能以增加“忽略父规则”长提示代替分离，也不能只修后台而使普通 CLI 丢失调度规则。

### I1：复用现有安装器

主要影响面：`platforms/codex.py` 的 initialize、_runtime_config_toml、validate_installation_profile；`scheduler_prompt.py`、现有 scheduler 模板及共同模板；现有托管块工具和安装夹具。

1. 项目 AGENTS 的框架托管块改为共同规则；用户块前后内容逐字保留。可识别的旧 scheduler 托管块原位迁移，未知或损坏标记按现有配置冲突路径处理，不猜测删除范围。
2. Root scheduler 通过现有项目托管配置生成 developer_instructions。正确处理 TOML 顶层 scalar 与 table 顺序，重复安装只生成一份内容。
3. 既有用户 developer 内容保留其来源和原文，先验证配置层覆盖效果，防止项目层遮蔽用户全局规则。由框架新增的角色段保持单独可更新边界，避免重复追加或把合并结果重新当用户原文。
4. 用户 developer 的适用范围无法机械判断时，使用现有安装冲突诊断明确列出冲突；不自动把用户全局规则提升为 Root-only，也不复制进每个 Worker 来猜测其范围。
5. 调度文字从 user 级移到 developer 级会改变优先级。逐条审查角色规则，只迁移框架职责和控制约定，不把用户科学偏好、题目目标或临时试验限制提升成框架不可变规则。
6. 安装在移除旧 scheduler 块前验证新配置和受控角色齐备；失败由现有事务恢复 AGENTS 与配置，避免半迁移。无需迁移数据库、冻结 assignment 或已封存结果。

最小夹具覆盖：用户 AGENTS 前后哨兵、已有顶层 developer、全局/项目层有效值、包含引号/多行的 TOML、重复安装、旧托管块、外部 workspace/launch-root、安装中途失败恢复。

### I2：两种 Root 与子角色共同验收

后台使用 `codex_progression.py` / `codex_root_host.py` 的现有配置加载入口；交互 CLI 依赖实际项目配置加载。两者消费同一 scheduler 源，避免另维护一份宿主提示。

- 新交互 Root：调度规则到达；fresh 受控 Worker 不收到 Root 专属段，仍收到用户共同规则及 Worker bootstrap。
- 后台 fresh Root、恢复与轮换：权限、目标、预算、未决提交与恢复材料不变；新线程角色提示正确。恢复旧线程可能保留历史 scheduler，不能宣称已清除。
- 受控 helper：沿现有 agent_type 配置得到 Worker 角色，保持与负责人相同的已声明权限。第三方科学插件复用统一生成逻辑，不写插件名分支。
- 用户自行配置的 native Agent：不改其文件；若它继承 Root 配置，明确这是框架未管理的角色，不承诺自动清理任意子会话。
- 未信任项目/更深目录配置覆盖：核对当前有效配置；受支持安装入口遇到 scheduler 缺失时给配置诊断。不能用重新塞回共享 AGENTS 全文作为默认退路。
- 更新实际涉及的架构、安装与角色文档及中英文对应章节；历史审计保留原结论，当前资格单独记录。

## 4. 成功标准与范围

1. 框架受控 Worker 的新会话不再投递 Root 专属 scheduler 正文；共同约束、用户项目原文、Worker 合同都存在。
2. 交互与后台 Root 收到同源调度规则；实例选择、阶段交接、可选独立审查与授权边界保持。
3. 分别统计共同块、Root developer、Worker bootstrap、assignment 及平台环境的字符/字节。以实际减少的职责无关内容验收，不声称整段 7,838 字符都可删除，也不预估 token/费用百分比。
4. 旧线程的已有消息不重写；需要干净上下文时使用现有新线程/轮换机制，保留科学状态与预算，不强行恢复或取消在途任务。
5. 第一轮范围仅含已有受支持 CLI 和后台入口；IDE 或用户自定义 Agent 未验证时如实列为范围外。
